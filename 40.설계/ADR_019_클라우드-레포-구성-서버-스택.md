# ADR - 019 클라우드 레포 구성·서버 스택

## 상태

채택 (2026-10-20, 설계). 구현(C1)에서 검증한다.

## 맥락

- PLAN 은 `euta-cloud` 레포 1개(서버·웹·러너), 전부 TypeScript, 엔진 그대로 import 를 정했다. 이 ADR 은 레포 안 구성과 서버·웹 프레임워크를 정한다.
- 확인한 사실(2026-10-20)
  - 엔진은 pnpm 9 워크스페이스, Node ≥ 22.13, TypeScript ~5.9, ESM(`"type": "module"`), 테스트 vitest.
  - 앱 렌더러는 React 19 + Vite 7. 단계 문장 생성기 `describeStep` 은 의존성 없는 하위 경로(`@euta/core/describe`)로 브라우저에서도 쓴다(ADR-018).
  - 공용 도구 핸들러 `@euta/mcp-server/tools` 는 transport 중립(ADR-008) — HTTP MCP 에 그대로 붙일 수 있다.
  - dev 클러스터 메모리 요청 한도 4Gi(PLAN "dev 호스팅") — 상주 프로세스 수를 줄여야 한다.

## 결정

### 1. 레포 구성 — pnpm 워크스페이스 4패키지

```
euta-cloud/
  packages/
    shared/   API 타입 · 권한 판정 · 검증 스키마 (서버·웹·러너 공용, 런타임 의존 최소)
    server/   API · 인증 · 스케줄러 · SSE · 원격 MCP · 결과 파일 저장 (Fastify)
    runner/   대기열 임대 → 엔진 하위 프로세스 → 이벤트·결과 업로드
    web/      웹 화면 (React + Vite) — 빌드 결과를 server 가 정적 파일로 제공
  deploy/     docker compose(로컬) · k8s 매니페스트(dev, ArgoCD 가 읽음)
```

- 엔진 의존은 ADR-001 과 같이 개발 중 `link:`(`../euta-engine/packages/*`), 이미지 빌드 때는 엔진 패키지를 tarball 로 묶어 넣는다(ADR-014 방식).
- **웹은 별도 서버를 두지 않는다** — server 가 빌드된 정적 파일을 같이 내보낸다. 쿠키 세션이 같은 출처에서 동작하고, dev 의 pod·메모리를 아낀다.
- 이미지 2종: `server`(API+웹+MCP), `runner`(Playwright 브라우저 포함). 러너만 무겁다.

### 2. 서버 — Node 22 + Fastify 5

- Fastify: 스키마 기반 요청 검증, 플러그인 구조, 스트리밍 응답(SSE·파일 내려받기)이 기본기. TypeScript 지원이 1급.
- 입력 검증 스키마는 `shared` 에 두고 서버·웹이 같이 쓴다(라이브러리는 구현 시 선택 — 엔진의 DSL 검증과 같은 계열 우선).

### 3. 웹 — React 19 + Vite

- 앱 렌더러와 같은 스택. 단계 문장 보기·폼 편집 화면을 앱에서 옮겨 오기 쉽다(공용 컴포넌트 패키지로 뺄지는 C4 에서 판단).

### 4. 러너 — 상주 Node 프로세스

- 실행 1건 = `euta run` 하위 프로세스(`child_process`, 새 임시 폴더). 엔진을 같은 프로세스에서 import 해 돌리지 않는다 — 브라우저·메모리 누수와 장애를 실행 단위로 끊기 위해.
- 이미지는 Playwright 공식 이미지(`mcr.microsoft.com/playwright`, 엔진 Playwright 버전과 같은 태그) 기반.

## 고려한 대안

| 대안 | 제외 이유 |
|---|---|
| Next.js(웹+API 한 덩어리) | 서버 기능(대기열·SSE·MCP·러너 연동)이 API 쪽에 몰려 있어 프레임워크 규약이 오히려 제약. 앱 React 컴포넌트 재사용은 Vite 로 충분 |
| Express | 검증·타입 지원을 따로 붙여야 함 |
| Hono | 가볍고 좋지만 Node 전용 기능(스트림·파일) 생태계는 Fastify 가 성숙 |
| 웹 별도 서버(nginx 등) | dev 메모리 한도 · 쿠키 세션 출처 문제 |
| 러너가 엔진을 in-process 로 실행 | 실행 하나의 장애·누수가 러너 전체에 번짐 |

### C4 1부 — 웹 패키지 실제화 (2026-10-21)

`packages/web` 가 자리에서 실제 React 앱이 됐다(결정 3 그대로). 레포 `euta-cloud` 커밋 `3a1d2a4`~`436b18f`.

| 항목 | 실제 |
|---|---|
| 스택 | React 19.3 · Vite 7.3(`@vitejs/plugin-react` 5) · TypeScript ~5.9 — 앱 렌더러와 같은 버전대. `@euta-cloud/shared` 를 `workspace:*` 로 써서 API 타입·토큰 만료 선택지·비밀번호 길이를 서버와 같은 값으로 |
| 빌드·동봉 | `vite build` → `packages/web/dist`(`index.html` + `assets/*`). 서버가 정적 파일 + SPA 대체(`/api` 밖 GET → `index.html`)로 내보냄 — `/device?user_code=…` 도 대체로 열린다. `pnpm dev` 는 `/api` 를 `localhost:8080` 으로 프록시 |
| 화면 | 가입 · 로그인 · 승인 대기 · 로그아웃 · 장치 승인 `/device` · 관리자(가입 승인) · 내 설정 > 토큰 + 로그인 뒤 첫 화면(안내). 한국어 UI, CSS 한 파일 |
| 라우터 | **직접 만든 작은 history 라우터**(경로 + 쿼리, `next=` 는 같은 사이트 경로만). 화면 7개에 react-router 를 들이지 않음 — 프로젝트·실행 화면(C4 본 작업)에서 중첩 경로가 필요해지면 그때 바꾼다 |
| 인증 호출 | Better Auth 클라이언트(`better-auth/react`) 대신 **같은 출처 `fetch`** 로 `/api/auth/*` 를 직접 부름(가입·로그인·로그아웃·장치 확인/승인/거부). 오류 코드는 euta 봉투 · Better Auth `code` · RFC 8628 `error` 셋 다 읽는다. 쿠키 세션이라 토큰을 웹이 다루지 않음 |
| 장치 승인 순서 | 로그인 확인(`GET /api/me`, 아니면 `/login?next=` 로 갔다 돌아옴) → `GET /api/auth/device?user_code=`(세션과 함께 — 코드가 이 계정에 묶임, ADR-023 결과) → 승인/거부 |
| 서버 보탬 | 공개 `GET /api/config` — `{ signUpMode: 'approval'\|'email', allowedEmailDomains }`. 가입 뒤 안내(승인 대기 / 메일 확인)를 고르는 데 필요 |
| 웹 E2E | Playwright `^1.64.1`(엔진·앱과 같은 줄, Chromium 캐시 재사용). `e2e/server.mjs` 가 compose PostgreSQL 에 새 DB 를 만들고 빌드된 서버(`dist/main.js`, 마이그레이션 포함)를 관리자 승인 모드로 띄움 → 끝나면 DB 삭제. `BASE_URL` = 브라우저가 여는 주소 그대로(`http://127.0.0.1:58180` — Better Auth 신뢰 출처·장치 `verification_uri`). 루트 `pnpm test:e2e`(= db:up → 전체 빌드 → Playwright). vitest(`pnpm test`)와 분리 |

- 고려한 대안: Better Auth React 클라이언트(번들·추상화가 지금 화면 수에 비해 큼) · react-router(위 라우터 항목) · 웹 E2E 를 vitest 안에(브라우저 구동·서버 프로세스 수명 관리는 Playwright `webServer` 가 맞음).
- 번들: JS 342 KB(gzip 105 KB) — shared 의 zod 가 함께 들어감(웹에서도 같은 검증 스키마를 쓰는 ADR 방침과 맞음).
- 검증: `pnpm -r typecheck` · `pnpm -r build` · `pnpm test`(221건) · `pnpm test:e2e`(2건) 통과.

### C4 2부 — 프로젝트·실행 화면 (2026-10-21)

프로젝트 목록 · 프로젝트 탭(현황 · 스크립트 · 실행 이력 · 실행 상세 · 예약 · 스위트 · 작업 로그 · 설정)을 냈다. 구현 결정은 [ADR-029](ADR_029_클라우드-웹-화면-구현.md). 이 ADR 의 결정 3("앱 렌더러와 같은 스택 — 공용 컴포넌트 패키지로 뺄지는 C4 에서 판단")에 대한 판단: **이번에는 앱 모듈을 복사**(편집 모델 · 단계 비교 · 동작별 폼)하고, 공용 패키지 추출은 두 레포에 걸친 작업이라 제안으로 남겼다(ADR-029 결과 "남은 일"). 라우터는 직접 만든 것을 패턴 매칭으로 넓혀 유지(react-router 미도입). 레포 `euta-cloud` 커밋 `a191d30`~`ea0977b`.

### C7 배포 준비 — 이미지 · dev 매니페스트 (2026-10-21)

| 항목 | 실제 |
|---|---|
| 서버 이미지 | `packages/server/Dockerfile` — `node:22-bookworm-slim`(메이저 태그만 — 패치 버전은 고정하지 않고 재빌드로 받는다, [ADR-040](ADR_040_Playwright-1.64.1-Node-보안-패치.md)), 사용자 `node`(1000). `scripts/stage-image.sh` 가 `packages/server/.docker`(git 제외)에 엔진 `@euta/core` 를 `pnpm pack` tarball 로(러너와 같은 ADR-014 방식, core 만) · 서버를 `pnpm deploy --prod`(package.json `files` = `dist`·`drizzle`) · 웹 빌드를 모은다. 이미지 안에서 core 를 `npm install --ignore-scripts`(브라우저 내려받기 없음 — 서버는 검증만) 하고 `node_modules/@euta/core` 를 그쪽으로 링크(호스트 형제 레포 `link:` 대체). `WEB_DIST` · `RESULTS_DIR=/data/results` 고정, 시작 시 마이그레이션 |
| 호스트 staging 을 고른 이유 | 서버 런타임 의존(`pg`·fastify·drizzle·better-auth·nodemailer·tar-stream)이 순수 JS 라 호스트(arm64 Mac)에서 모은 `node_modules` 를 amd64 이미지에 그대로 넣어도 된다. 대안(빌드 단계에서 linux 로 `pnpm install`)은 lockfile 의 `link:../../../euta-engine` 을 컨텍스트에 재현해야 해 복잡. better-auth 의 peer `vitest` 가 끌고 오는 vite·esbuild·rolldown(호스트 플랫폼 바이너리)은 런타임에 쓰지 않아 staging 에서 지운다. **나중에 네이티브 의존이 생기면 이 방식은 깨진다** — 그때 빌드 단계 설치로 바꾼다 |
| 크기(amd64) | 서버 약 500MB(압축 약 100MB) · 러너 약 3.6GB(압축 약 1GB, Playwright 이미지가 대부분) |
| 상태 확인 | `/healthz`(프로세스, 공개·내부 리스너) + **`/readyz`** 신설(공개, DB `select 1`, 실패 503 `NOT_READY`) |
| 매니페스트 | `euta-cloud/k8s/dev/` kustomize(ArgoCD App Path). PostgreSQL 17 StatefulSet(PVC 5Gi, `PGDATA` 하위 폴더) · 서버 Deployment(PVC 14Gi 를 `/data` 에, `fsGroup` 1000 · startupProbe 5분) · Service 8080/8081 · Ingress(`public` · 와일드카드 TLS · SSE 용 버퍼링 끔·읽기 3600초 · 본문 2m) · 러너 Deployment(동시 2, `/dev/shm` 메모리 1Gi, `shareProcessNamespace` 로 브라우저 고아 프로세스 회수 — Playwright 이미지에 tini 없음). 이미지 `<사내 이미지 저장소>/euta/…:<TAG>`(저장소 프로젝트 `euta`, 태그는 push 때 채움). 풀 시크릿은 배포 환경이 주는 공용 풀 시크릿 먼저, 안 되면 사용자가 만든 pull 전용 로봇 계정 시크릿으로 교체(README) |
