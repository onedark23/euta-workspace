# ADR - 021 클라우드 결과 파일 저장

## 상태

채택 (2026-10-20, 설계). 구현(C1)에서 검증한다.

## 맥락

- 실행 결과 폴더(스크린샷·실패 시 영상·trace·HAR·console·artifacts·report.html)를 클라우드에 보관하고, 웹·로컬 앱이 **열 때** 받아 간다(PLAN "동기화·충돌").
- dev 한도: 저장소 요청 20Gi, 메모리 요청 4Gi. 저장소는 ceph-rbd(PVC). RWO 볼륨은 여러 노드의 pod 가 동시에 붙을 수 없다.
- 처음 ARCH 초안은 별도 오브젝트 저장소(S3 호환 서버)를 두었다.

## 결정

### 1. 저장 인터페이스 + 1차 구현은 서버 PVC 파일 시스템

- 서버 안에 `ResultStore` 인터페이스(`put(runId, 상대 경로, 스트림)` · `get` · `list` · `deleteRun`)를 두고, **1차 구현은 서버 pod 의 PVC 디렉터리**에 저장한다.
- **러너는 저장소에 직접 쓰지 않는다.** 실행이 끝나면 결과 폴더를 묶어 서버 API 로 올리고(러너 인증, 실행 id 단위), 서버가 풀어 저장한다. 웹·앱은 서버 API 로 파일을 받는다(권한 판정 포함).
- 경로: `<root>/<projectId>/<runId>/…` — 엔진 결과 폴더 구조 그대로.
- S3 호환 구현은 운영 정식화 또는 서버를 여러 대로 늘릴 때 같은 인터페이스로 추가한다.

### 2. 보관 정리

- 서버 정리 작업이 결과 파일을 **기간 + 전체 용량 상한** 기준으로 지운다(오래된 것부터). 요약·지표·expect 결과·색인(DB)은 남긴다. 기간·상한 값은 SPEC 에서 정한다.
- 시각 비교 기준 이미지는 실행 결과와 따로 두고 정리 대상에서 뺀다(`<root>/<projectId>/baselines/<환경>/<실행 위치>/`).

### 3. 업로드 형식

- 러너 → 서버: 결과 폴더를 tar 스트림 1개로 업로드(파일 수가 많아도 요청 1번). 서버는 경로 탈출(`..`·절대 경로) 항목을 거절한다.
- 업로드가 끝나야 실행을 최종 상태로 바꾼다. 업로드 실패 시 러너가 재시도, 끝내 실패하면 "중단"(요약은 이벤트로 이미 들어와 있음).

## 고려한 대안

| 대안 | 제외 이유 |
|---|---|
| 클러스터 안 S3 호환 서버(MinIO·SeaweedFS 등) | pod·메모리 하나 추가(4Gi 한도), 운영 대상 증가. MinIO 커뮤니티판은 배포 정책 변화로 이미지 확보도 불확실 |
| 러너와 서버가 같은 볼륨 공유 | RWO 볼륨은 다른 노드 pod 와 공유 불가, RWX 는 storageClass 보장 없음 |
| DB 에 파일 저장 | 영상·trace 크기 · DB 백업 비대 |

## 결과

이 결정으로 ARCH "배포·운영" 자원 배분의 오브젝트 저장소 줄이 서버 PVC 로 바뀐다.

### C1 서버 2부 — 실행·러너 (2026-10-20)

결정대로 구현했다. 레포 `euta-cloud` 커밋 `4e8eab4`·`85d6e1c`(서버) · `c0affbe`(러너).

| 항목 | 실제 |
|---|---|
| 인터페이스 | `ResultStore` — `put · get · list · deleteRun · deleteProject` + 기준 이미지 `putBaseline(추가만) · listBaselines · getBaseline`. 1차 구현 `FsResultStore(RESULTS_DIR)` |
| 경로 | `<root>/<projectId>/<runId>/…` = 엔진 결과 폴더 내용 그대로(`run.json · steps.jsonl · run.log · report.html · metrics.json · network.har · console.jsonl · screenshots/ · diffs/ · video/ · artifacts/ · trace.zip`). runs 디렉터리의 `index.sqlite` 는 올리지 않는다. id 는 `[A-Za-z0-9_-]` 만, 상대 경로는 `..`·빈·`.` 조각·절대·드라이브·역슬래시·제어 문자를 거절하고 풀린 경로가 루트 안인지 다시 확인 |
| 업로드 | `PUT /internal/runs/:id/result`(`application/x-tar`, 러너 토큰 + 임대 보유 러너만). `tar-stream` 3.2 로 흘려 읽으며 항목마다 검사 — **파일·디렉터리만**(심볼릭·하드 링크·장치 → 422 `TAR_REJECTED`), 안전하지 않은 경로 → 422, 내용 합계 > `RESULT_MAX_RUN`(기본 2Gi) → 413. 위반이면 그때까지 쓴 파일을 모두 지운다. 재시도는 이전 부분 업로드를 지우고 새로 씀 |
| 종료 순서 | `finish` 는 업로드(`result_files = present`) 뒤에만 받음(아니면 409 `RESULT_NOT_UPLOADED`). 러너가 업로드를 4번(1·2·4초 간격) 실패하면 `uploadFailed` 로 종료 → 실행 `aborted`, 남은 부분 파일 삭제. 임대 만료로 `aborted` 된 실행의 부분 파일도 삭제 |
| 내려받기 | `GET …/runs/:runId/files`(목록) · `…/files/*path` — 보기 권한 이상. 이미지·영상·JSON·텍스트는 알려진 형식으로, 그 밖(다른 HTML 포함)은 `application/octet-stream` + `attachment`. 모든 응답 `x-content-type-options: nosniff`, CSP `default-src 'none'; sandbox`. `report.html` 만 `text/html` + 스크립트 없는 CSP(`img-src 'self'` 등) — 엔진 리포트는 스크립트가 없다. `GET …/report` 는 `files/report.html` 로 302(리포트의 상대 링크 `screenshots/…` 가 그대로 동작) |
| 보관 정리 | `purgeResults`(서버 1시간 주기): 종료 30일(`RESULT_RETENTION_DAYS`) 지난 실행 파일 삭제 → 남은 합계가 `RESULT_MAX_TOTAL`(12Gi)을 넘으면 오래 끝난 실행부터 삭제. 합계는 DB 의 실행별 크기로 계산(디스크 순회 없음). 삭제된 실행은 `result_files = expired`, DB 요약·단계·지표·expect 는 남음(1년 — ADR-020). 프로젝트 영구 삭제 때 프로젝트 디렉터리 통째 삭제 |
| 기준 이미지 | `<root>/<projectId>/baselines/<envId>/<실행 위치 slug>/` — 정리 대상 아님. 러너는 서버 PVC 를 볼 수 없으므로 **서버 경유 동기화**: 실행 전 `GET /internal/runs/:id/baselines`(tar)를 임시 기준 폴더에 풀고 엔진 `--baseline-dir` 로 넘김 → 실행 뒤 엔진이 새로 만든 기준만 `PUT …/baselines`(추가만, 있는 파일은 덮지 않음). 환경 폴더 이름은 이름 대신 id(이름 변경에 안전, 로컬 앱 `baselines/<envId>/` 와 같음) |

- 검증: tar 탈출 5종(`..`·절대·`a/../../`·심볼릭·하드 링크) 거절 + 파일 0개, 크기 상한 413, 파일 형식·리포트 302·경로 탈출 URL 404, 보관 30일·용량 상한(시계 주입)·1년 뒤 실행 삭제, 기준 이미지 추가만·정리 제외 — `packages/server/test/runs.test.ts`. 실제 엔진 결과 폴더 형식·`on-failure` 녹화 삭제/보존은 러너 E2E.
- 남은 일: S3 호환 구현은 서버 여러 대 / 운영 정식화 때(같은 인터페이스).
