# ADR - 022 클라우드 실시간 전송

## 상태

채택 (2026-10-20, 설계). 구현(C2·C3)에서 검증한다.

## 맥락

- 실시간이 필요한 곳은 두 방향이다.
  - **서버 → 웹·앱**: 프로젝트를 연 동안 다른 사람의 저장 · 실행 시작/종료 · 진행 단계 · 설정 변경. 재연결 시 놓친 변경을 받아야 한다(ARCH "변경 받기").
  - **러너 → 서버**: 실행 중 엔진 이벤트(ADR-007 — `step.*` · `metric.recorded` · `expect.evaluated` 등).
- 클라이언트 → 서버 요청(저장·실행 요청)은 일반 HTTP API 로 충분하다.

## 결정

### 1. 서버 → 웹·앱: SSE (Server-Sent Events)

- 프로젝트별 스트림 `GET /api/projects/:id/events`. 이벤트마다 변경 순번(ADR-020 변경 피드)을 `id:` 로 싣는다.
- 재연결 시 `Last-Event-ID` 로 마지막 순번을 보내면 서버가 그 뒤 변경부터 보낸다. 보관 기간을 넘었으면 "전체 다시 받기" 신호를 보낸다.
- 서버가 여러 대여도 같은 변경을 보도록 변경 발생 시 DB `NOTIFY` → 각 서버가 자기 연결에 전달.
- 진행 단계처럼 잦은 이벤트는 실행별로 묶어(예: 0.5초) 보낸다.
- ingress: 응답 버퍼링 끔 · 긴 읽기 시간 제한(nginx ingress 주석) · 서버가 주기적으로 주석 줄(`:`)을 보내 연결 유지.

### 2. 러너 → 서버: HTTP 일괄 전송

- 러너가 엔진 하위 프로세스의 이벤트(`steps.jsonl` 과 같은 줄)를 모아 1초 또는 N건마다 `POST /internal/runs/:id/events` 로 보낸다. 임대 연장도 같은 요청에 싣는다.
- 서버는 이벤트로 실행 요약을 갱신하고 SSE 로 퍼뜨린다. 최종 결과 파일은 ADR-021 업로드가 정본.

## 고려한 대안

| 대안 | 제외 이유 |
|---|---|
| WebSocket | 양방향이 필요 없음. 재연결·이어 받기를 직접 구현해야 함. SSE 는 HTTP 그대로라 인증 쿠키·토큰·ingress 가 단순 |
| 폴링만 | 진행 표시가 늦고 요청이 많음. SSE 장애 시 대체 경로로만 둔다 |
| 러너 → 서버도 SSE/WebSocket | 러너가 보내는 쪽이라 짧은 POST 반복이 단순하고 실패 재시도가 쉬움 |

## 결과

### C1 서버 1부 — 서버 → 웹·앱 SSE (2026-10-20)

§1 을 구현했다(§2 러너 → 서버는 실행·러너 작업에서).

- `GET /api/projects/:id/events` — 보기 권한 이상. `id:` = 프로젝트 변경 순번(ADR-020 변경 피드), `event: change` 의 data = `{ seq, kind, at, actorId, data }`.
- 이어 받기: `Last-Event-ID` 헤더(EventSource 재연결) 또는 첫 연결용 `?lastEventId=`. 위치 없이 연결하면 `event: ready`(현재 순번)부터. 요청 위치 이후가 보관 기간(7일)을 넘어 지워졌거나 미래 위치면 `event: resync`(현재 순번) — 클라이언트가 전체를 다시 읽는다.
- 여러 서버: 변경 트랜잭션의 `pg_notify` → 각 서버의 LISTEN 연결 → 해당 프로젝트 구독 연결이 DB 에서 빠진 순번부터 읽어 보냄(중복·순서 보장). 서버 2대 테스트 통과.
- 응답 헤더 `cache-control: no-cache` · `x-accel-buffering: no`, 25초마다 주석 줄로 연결 유지, `retry: 3000`. 진행 단계 묶음 전송(0.5초)은 실행 이벤트가 생기는 다음 작업에서.

### C1 서버 2부 — 러너 → 서버 (§2) (2026-10-20)

§2 를 구현했다. 레포 `euta-cloud` 커밋 `4e8eab4`(서버) · `c0affbe`(러너).

- 러너는 엔진 하위 프로세스의 `<runs-dir>/<엔진 실행 id>/steps.jsonl` 을 200ms 간격으로 이어 읽어(엔진이 이미 secrets 를 가린 줄) **1초 또는 50건**마다 `POST /internal/runs/:id/events` 로 보낸다. 보낼 것이 없어도 **5초**마다(`RUNNER_HEARTBEAT_MS`, 임대 응답에 실어 알려 줌) 빈 묶음을 보내 임대를 연장한다(만료 2분). SPEC 의 30초 연장 주기보다 짧게 한 이유: 취소·시간 초과 신호가 이 응답으로 전달되므로 대기 스텝 중에도 수 초 안에 엔진을 멈추려고.
- 응답 `{ stop: null | 'cancel' | 'timeout', leaseExpiresAt }`. 임대를 잃었으면(다른 러너·취소 완료·만료) 409 `LEASE_LOST` → 러너는 엔진을 멈추고 그 실행을 버린다(업로드·종료 안 함).
- 서버는 묶음을 한 트랜잭션에서 반영 — 이벤트 `seq` 로 중복 무시(재전송 안전), 첫 묶음에서 `leased → running`, `step.started` → 현재 단계, `step.finished` → 단계 색인(오류 2,000자), `metric.recorded` → 지표, `expect.evaluated` → 조건·통과 여부·기대/실제(각 500자), `run.finished` → 요약. 원본 이벤트는 DB 에 두지 않는다(정본은 업로드된 `steps.jsonl`).
- **SSE 진행 묶음**: 단계 이벤트가 든 묶음마다 변경 피드에 `run.progress` 1건(현재 단계·끝난 단계 수). 러너 쪽 1초 묶음이 곧 진행 묶음 전송이라 서버에서 0.5초 묶음을 따로 두지 않았다(실행 1건당 초당 최대 1건, 대기 스텝 중에는 0건).
- 실행 피드 종류: `run.requested`(작업 로그에도) · `run.leased` · `run.started` · `run.progress` · `run.cancel_requested`(작업 로그에도) · `run.timeout_requested` · `run.finished` / `run.cancelled`(작업 로그에도). data 에 `runId`(스위트 자식은 `parentRunId`)·상태·요약.

### C3 서버 — 앱 알림 `GET /api/me/events` (2026-10-21)

레포 `euta-cloud` 커밋 `b0bca84`.

- 프로젝트 피드(`change_feed`)의 순번은 프로젝트별이라 여러 프로젝트를 한 커서로 이어 받을 수 없다 → **받는 사람별 행** 테이블 `user_events`(전역 `bigserial` id = SSE `id:`)를 따로 둔다. 예약 실행 알림은 프로젝트 구성원(소유자·편집자) 수만큼, 내 실행 종료는 요청자 1행.
- 순서 보장: 삽입 때 `pg_advisory_xact_lock(hashtext('euta_user_events'))` 를 잡아 id 발급~커밋을 직렬화 → id 순서 = 보이는 순서(늦게 커밋된 작은 id 를 건너뛰는 일이 없다). 이 잠금은 **트랜잭션의 마지막 문장**에서만 잡는다(잡은 뒤 다른 잠금을 기다리지 않으므로 교착 없음). 예약 틱처럼 뒤에 쓰기가 남은 경우는 모아 두었다가 마지막에 넣는다.
- 깨우기: `NOTIFY euta_user_events`(빈 payload) → 서버마다 열린 사용자 스트림이 각자 `id > 마지막 전송` 을 다시 읽음(사용자별 채널 대신 — 8KB payload·채널 수 걱정 없음, 연결 수가 작아 재조회 비용 무시).
- 이어 받기·다시 받기: 위치 없이 연결 → 지금 위치(`max(id)`, 시퀀스 값이 아님 — 잠금 안에서 아직 커밋 안 된 id 를 건너뛰지 않도록)부터. 요청 위치 < (남아 있는 최소 id − 1) 이면 그 사이가 지워졌을 수 있으므로 `resync`. 보관 = 피드와 같은 `FEED_RETENTION_DAYS`(7일), `purgeExpired` 가 정리.
- 이벤트 형식: `event: notification`, data = `UserEventDto`(`kind` = `failure · recovery · passed · flaky · skipped · aborted · run.finished`). 연결 유지 주석 25초, `retry: 3000` — 프로젝트 피드와 같음. 서버 2대 테스트(다른 인스턴스에서 쓴 이벤트 실시간 수신) 통과.
