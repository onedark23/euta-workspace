# ADR - 046 TC 변환 자동 진행

## 상태

채택 (2026-11-05). 단계 16-4 의 앱 구현. euta-app 브랜치 `feat/tc-auto-convert` 커밋 c1f0e41(AI 저장 전 검증) · 6b88c92(거절된 저장 버리기 보정) · a0b9715(자동 진행) · af493f4(실사용 비교 지침 4줄) · da31be2(보내지 못한 항목의 변환 중 풀기) · c0a8c63(앱 재시작 뒤 처음 쓸 때 남은 변환 중을 대기로 — 턴 도중 앱이 꺼진 경우, `TcDocStore.releaseAll`). main 합침 2026-11-06(fast-forward).

## 맥락

- 실사용(사내 시범 사이트, 2026-11-04~05)에서 [AI로 변환] 이 첫 메시지 `tcConvert: <docId>` + 대기열 전체를 넘기자 AI 가 대기열을 한 메시지 안에서 돌다 사전 조건 1 + TC 5 만에 왕복 한도(`MAX_TURNS` 60)에 닿아 채팅이 `error_max_turns` 오류로 끝났다.
- 클라우드 프로젝트에서 AI 가 `expect.visible` 에 `level: 1` 을 써서 저장했고, 서버가 "Unrecognized key: level" 로 거절해 보내기 대기열 전체가 멈췄다. 그 뒤 AI 가 고친 저장은 거절 건 뒤에서 기다렸고, [내 저장 버리기] 는 새 파일이라 서버 것을 받으려다 404 → 로컬 파일 삭제 + 같은 경로의 뒤 저장(고친 것)까지 지웠다.
- SPEC "AI 변환" 이 2026-11-05 에 바뀜: 메시지 하나 = 항목 하나, 앱이 다음 항목을 자동으로 보냄, 한도에 닿으면 한 번 더 · 두 번이면 실패, 진행 개수, [중지], AI 저장 전 검증, 판정 느슨화 금지.

## 결정

### 턴이 어떻게 끝났는지를 엔진이 돌려준다 — `ChatEngine.send() → TurnOutcome`

- `send()` 가 `{ kind: 'success' | 'max-turns' | 'aborted' | 'error', subtype?, message? }` 로 끝난다. SDK `result` 의 `subtype === 'error_max_turns'` 가 `max-turns`, 그 밖의 실패 결과 · 예외 · 결과 없음은 `error`, Stop 은 `aborted`.
- 채팅 알림도 맞췄다: 왕복 한도는 오류가 아니라 정보 알림 "이 메시지의 AI 왕복 한도(60회)에 닿아 여기서 멈췄습니다". 다른 실패 결과는 그대로 오류 알림. 모든 채팅에 적용(자동 변환 전용 아님).
- `ChatEngine.note(chatId, level, text)` — 턴 사이에 앱 알림을 채팅에 남긴다("한 번 더 보냅니다", 자동 변환 끝 요약).

### 자동 진행 루프는 main 의 `TcDocs` 가 돈다

- `convert()` 는 대기열을 저장하고 새 채팅을 만든 뒤 루프를 시작한다(기다리지 않음). 첫 메시지는 `convert()` 가 돌아가기 전에 동기적으로 나간다(돌려준 채팅이 이미 busy).
- 다음 항목 `nextConvertItem(doc)`: 대기열 앞 TC(완료 · 제외는 건너뜀). 그 TC 의 사전 조건이 아직 끝나지 않았으면(완료 · 실패 · 제외가 아님) **사전 조건이 먼저**. 실패한 사전 조건은 막지 않는다 — TC 메시지에 "실패 — TC 스크립트는 각자 로그인부터" 를 적어 보낸다.
- 메시지 형식 `itemPrompt()`: 첫 줄 `TC 문서 "<이름>" 자동 변환 (n / N) — …`(채팅 제목이 됨), 둘째 줄 `tcConvert: <docId> <tcId | pre-<n>>`. 사전 조건 메시지는 문장 · `파일: pre-<n>-<slug>.yaml` · 쓰는 TC. TC 메시지는 할 일 한 줄 + 판정 규칙(느슨화 금지) + 실사용 비교 지침 4줄. 재시도면 `(재시도 2/2)` 와 "저장한 스크립트를 read_file 로 읽고 이어서". [다시 변환] 문구와 **덧붙일 말은 메시지마다** 붙인다(앞 메시지가 길어져도 지시가 빠지지 않게).
- 보내는 순간 그 항목을 `변환 중`(채팅 id)으로 표시한다(사전 조건도). 턴이 끝나면 기존 `releaseChat` 이 끝나지 않은 항목을 `대기` 로 되돌린다.
- 메시지가 끝난 뒤 판단 (`itemFinished`: TC = 대기열에서 빠졌거나 완료 · 실패 · 제외, 사전 조건 = 완료 · 실패 · 제외):
  1. 끝났으면 TC 는 진행 수 +1.
  2. `aborted`(사람이 [중지] · 채팅 Stop) → 멈춤. 끝난 항목이라도 멈춘다(사람이 멈추려 한 것).
  3. 끝났으면 다음 항목.
  4. `error` → 멈춤(그 항목은 `대기`).
  5. `max-turns` 또는 **기록 없이 정상으로 끝남** → 같은 항목을 한 번 더. 두 번째도 안 끝나면 `실패`(note "두 번 시도에도 끝나지 않음", 작업 로그 `tcdoc.converted`)로 두고 다음 항목.
- 보내기 자체가 실패하면(채팅이 바쁨 · 없음 — 턴이 돌지 않아 턴 끝 되돌리기가 없음) 루프가 끝날 때 그 채팅의 `변환 중` 을 `releaseChat` 으로 되돌린다.
- 멈춤 조건: 대기열 빔(`empty`) · [중지](`stopped`) · 진행 개수 도달(`limit`) · 오류(`error`). 대기열이 비었는지를 개수보다 먼저 본다(개수 = 대기열 길이일 때 "다 마침" 으로 보이게). 끝나면 채팅에 요약 알림, 문서에 `lastRun`(메모리) 을 남긴다. 대기열은 그대로라 [이어서 변환] 이 같은 방식으로 새 채팅에서 시작한다.
- **진행 개수는 TC 만 센다**. 사전 조건 스크립트는 TC 의 준비 단계라 세지 않는다(메시지 수는 그만큼 늘 수 있어 대화상자 안내에 "사전 조건이 필요하면 1개 더").

### 잠금은 루프 전체에 걸린다

- 예전 잠금(`converting: Map<key, chatId>`)은 턴이 끝날 때 풀리고 `chat.busy` 가 아니면 무시됐다 → 항목 사이(채팅이 busy 아님)에 두 번째 시작이 끼어들 수 있다. 잠금을 `runs: Map<key, AutoRun>` 으로 바꾸고 루프의 `finally` 에서만 지운다. `chatTurnEnded` 는 `releaseChat` · 가져오기 상태만 다룬다.
- 그 채팅에 사람이 메시지를 보내면(`ai:send`) "TC 자동 변환이 진행 중입니다 — [중지] 한 뒤 보내세요" 로 거절한다. 화면도 입력칸을 끄고 안내한다(항목 사이에 사람 메시지가 끼면 다음 항목 보내기가 busy 로 실패하기 때문).

### 진행 표시는 문서 보기 + 별도 조회로

- `TcDocView.progress`(`done · total · current{ tcId, title, precondition?, preconditionText?, attempt } · stopping`)와 `lastRun`(`reason · done · total · message`). 둘 다 메모리 — 재시작하면 사라진다(대기열은 저장돼 있음).
- 채팅 화면은 `tcdoc:progress(projectId)` 로 진행 중인 자동 변환 목록을 받아 그 채팅 것을 보인다(`tcdoc:changed` 마다 다시 읽음). 진행 정보를 `ChatView` 에 넣지 않은 이유: `ChatView` 는 `chats/<id>.json` 에 저장된다.
- 화면: TC 문서 상세의 동작 카드와 채팅 머리 아래에 같은 띠 — "**n / N** 진행 중 · 지금 **<TC 제목>** <TC ID 작게>"(사전 조건이면 "· 사전 조건 스크립트 먼저: "<문장>"", 재시도면 "· 한 번 더 (한도에 닿음)") + 테두리 있는 [중지] 버튼(아이콘 + 글자, 툴팁). n = 지금 메시지의 순번(마친 수 + 1). 채팅 입력칸 옆 [멈추기] 도 자동 변환 중에는 [중지] 와 같다. 끝나면 상세에 "지난 자동 변환: <이유> — n / N 마침".
- 대기열 확인 대화상자: "자동으로 진행할 개수" 숫자 칸(기본 = 대기열 전체, 1 ~ 전체) — 넘는 순번은 흐리게 "대기열에 남음", 안내 "항목마다 AI 메시지 1개를 씁니다(사전 조건이 필요하면 1개 더) — 본인 Claude 구독 사용량에서 나갑니다", [변환 시작 (개수)].
- IPC: `tcdoc:stop(projectId, docId)` · `tcdoc:progress(projectId)`, `tcdoc:convert` 에 `limit`.

### AI 지침

- `TC_GUIDE`(시스템 프롬프트)를 "메시지 하나 = 항목 하나 — 그 항목을 기록하면 한 줄 보고하고 끝낸다, 다음 항목은 앱이 보낸다" 로 바꿨다. 재시도 표시의 뜻, 실패한 사전 조건이어도 TC 는 변환, 판정 느슨화 금지(띄어쓰기 허용 · 부분 일치 · 정규식 느슨화 · 검사 빼기 금지, 실패로 두고 note), 실사용 비교 지침 4줄(문구는 `^…$` 전체 일치 · "기억 → 비교" 는 `vars` 고정, 적어 두기만 하는 `manual` 금지 · 데이터를 바꾸는 TC 는 이름으로 특정 · 되돌림 확인 · 개수 범위 좁히기 · 스키마 키만, 모르면 `get_schema`), `save_script` 가 먼저 검증한다는 것.
- `set_tc_conversion` 결과의 `next`(다음 TC) 를 빼고 `then: "Report one line … Do not start another queue item"` 으로 바꿨다 — 남은 대기열을 보고 AI 가 다음 TC 로 넘어가지 않게.

### AI 저장 전 검증 (B1) — `save_script`

- 쓰기 전에 `saveCheck(yaml)` — **클라우드 서버의 저장 검사(`script-check.ts`)와 같은 규칙**: YAML · 스키마 · 참조 문법, `${env.*}` · `${secrets.*}` 값은 자리값. 문제가 있으면 아무것도 쓰지 않고 `{ error: "script NOT saved…", issues }` 도구 오류. 로컬 · 클라우드 프로젝트 모두(클라우드면 보내기 대기열 `ai_mcp` 에 들어가지 않는다).
- 저장 뒤의 `{ savedTo, valid, issues }` 는 그대로 — 채팅 환경 기준 검사(없는 비밀값 이름 등)는 저장을 막지 않는 정보.
- `session_export` 는 엔진 핸들러가 직접 쓰므로 이 검사 밖이다. 세션에서 통과한 단계로 만든 YAML 이라 범위에서 뺐다.

### 거절된 저장 버리기 (B2) — `ProjectSync.resolve(…, 'theirs')`

- 거절(rejected) 건을 버릴 때 **같은 스크립트의 뒤 저장이 대기열에 있으면 그 거절 건만 빼고** 뒤 저장을 보낸다. 서버 것을 받지 않으므로 로컬 파일은 그대로(새 파일도 지워지지 않음). 뒤 저장이 없으면 예전대로(서버 것 받기, 없으면 로컬 삭제). 충돌(conflict) 버리기는 바꾸지 않았다(같은 경로 뒤 저장도 모두 버림 — 뒤 저장은 버린 내용 위에 쓴 것이므로).
- 화면: `CloudConflictView.laterSaves`(뒤 저장 수). 거절 대화상자에서 뒤 저장이 있으면 "이 스크립트의 뒤 저장이 N개 더 있습니다…" 안내와 버튼 [이 저장만 버리기 (뒤 저장 N개 보내기)].

## 이유

- 메시지마다 왕복 한도가 새로 주어지므로 한 TC 가 길어도 대기열 전체가 끝나지 않는 일이 없다. 같은 채팅(SDK 세션 이어 쓰기)이라 앞 항목에서 확인한 화면 정보를 그대로 쓴다.
- 루프를 main 에 둔 것: 렌더러가 닫히거나 다른 탭에 있어도 진행되고, 잠금 · 상태 기록 · 실패 처리를 한 곳에서 한다.
- "기록 없이 정상 종료" 도 재시도 대상으로 본 것: SPEC 은 "두 번 연속 끝나지 않으면(완료 · 실패 · 제외가 아님) 실패" — 한도로 끝났든 AI 가 기록을 빼먹었든 같은 처리가 단순하고, 무한 반복이 없다.
- 덧붙일 말을 메시지마다: 비용(짧은 글)보다 지시가 빠지지 않는 쪽이 낫다.
- 저장 전 검증을 서버 규칙과 같게: 앱이 서버보다 엄격하면(예: 아직 등록 안 된 비밀값) 정상 스크립트를 못 저장하고, 느슨하면 대기열이 다시 멈춘다.

## 고려한 대안

- `MAX_TURNS` 를 올리기 — 대기열이 길면 같은 문제, 구독 사용량 보호 목적과 어긋남.
- AI 가 대기열을 돌되 한도에 닿으면 앱이 "계속" 메시지 보내기 — 한 메시지에서 어디까지 했는지 앱이 알 수 없고 판단이 AI 에 달린다.
- 진행 정보를 `ChatView` 에 넣기 — 채팅 파일에 저장돼 재시작 뒤 낡은 진행이 보인다.
- 사람 메시지를 항목 사이에 허용 — 다음 항목 보내기와 경합하고, AI 가 어느 지시를 따를지 모호해진다. [중지] 후 대화하고 [이어서 변환] 으로 계속하게 했다.
- 거절 버리기에서 뒤 저장을 그 자리에서 다시 보내기 대신 "다시 보내기" 를 쓰게 하기 — 거절된 내용은 서버가 또 거절한다.
