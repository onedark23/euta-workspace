# ADR - 023 클라우드 인증 구현

## 상태

채택 (2026-10-20, 설계). 구현(C1·C2·C5)에서 검증한다. 라이브러리 기능은 2026-10-20 Context7 문서(Better Auth v1.6.23)로 확인했고, 실제 동작은 구현 때 테스트로 확인한다.

## 맥락

- PLAN: 회사 도메인 한정 자체 가입(이메일·비밀번호 + 메일 인증), 사람 로그인만 **Entra ID 로 갈아끼울 수 있는 구조**, 웹·로컬 앱·MCP 는 euta cloud 가 발급한 자격으로, MCP 는 **계정별 개인 토큰**(접두사 · 해시 보관 · 만료 · 폐기).
- 인증을 직접 구현하면(비밀번호 해시·세션·메일 인증·재설정·토큰) 보안 실수 위험이 크다.
- 확인한 사실(Better Auth v1.6.23 문서, 2026-10-20)
  - `emailAndPassword.requireEmailVerification` + `emailVerification.sendVerificationEmail` 로 인증 전 로그인 차단.
  - `hooks.before` 에서 `/sign-up/email` 요청의 이메일 도메인 검사 → 거절 가능.
  - API 키 플러그인(`@better-auth/api-key`): 키별 `prefix` · `expiresIn` · `permissions`, `verifyApiKey`, 헤더 추출 방식 지정(`customAPIKeyGetter`).
  - 장치 인가 플러그인(`deviceAuthorization`, RFC 8628): CLI·데스크톱이 코드 요청 → 브라우저에서 승인 → 폴링으로 토큰 수신. Bearer 플러그인으로 API 호출.
  - 소셜 공급자 `microsoft`(Entra ID): `tenantId` 로 사내 테넌트 한정 가능.
  - Drizzle 어댑터 제공(ADR-020).

## 결정

### 1. Better Auth 를 서버 인증 계층으로 쓴다

| 필요 | 쓰는 기능 |
|---|---|
| 회사 도메인 한정 가입 | 이메일·비밀번호 + `hooks.before` 도메인 검사(허용 도메인은 설정값) |
| 메일 인증 | `requireEmailVerification` + `sendVerificationEmail`(아래 메일 발송) |
| 웹 세션 | Better Auth 세션 쿠키(httpOnly · SameSite=Lax · 같은 출처 — ADR-019 웹 동봉) |
| **로컬 앱 로그인** | **장치 인가 플러그인** — 앱이 코드 요청 → 시스템 브라우저로 승인 화면(이미 웹 로그인돼 있으면 승인만) → 앱이 폴링으로 토큰 수신 → OS 보안 저장소 보관 → Bearer 로 API 호출 |
| MCP 개인 토큰 | API 키 플러그인 — 접두사 `euta_`, 만료 필수(기본 90일·최대 1년, SPEC 확정), `permissions` 로 scope(`read`/`write`) 표현, `Authorization: Bearer` 에서 추출 |
| 관리자 | 사용자 비활성화 시 세션·API 키 일괄 무효(구현 시 플러그인 동작 확인, 부족하면 서버에서 보강) |
| 나중 — Entra ID | `socialProviders.microsoft`(사내 `tenantId`) 추가 + 이메일/비밀번호 가입 끄기. 기존 사용자는 같은 이메일로 계정 연결 |

- 프로젝트 역할(소유자·편집자·보기) 판정은 Better Auth 조직 기능을 쓰지 않고 **서버 자체 권한 모듈**(`shared` 의 판정 함수)로 한다 — 역할이 프로젝트 단위이고 규칙이 단순해 라이브러리 모델에 맞추는 비용이 더 크다. Better Auth 는 "누구인가" 까지만.
- ARCH 초안의 "로컬 앱 = 루프백 리다이렉트 + PKCE" 는 장치 인가로 바꾼다 — 앱이 로컬 포트를 열 필요가 없고 같은 라이브러리로 끝난다.

### 2. 메일 발송

- 인증·비밀번호 재설정 메일은 SMTP 로 보낸다. **사내 SMTP(릴레이) 정보가 필요하다 — 미확인.**
- 로컬 개발은 메일 수신 확인용 도구(docker compose 안 가짜 SMTP)를 쓴다. dev 에서 SMTP 를 못 구하면 임시로 관리자 승인 방식(관리자가 가입 계정을 활성화)으로 대체할 수 있게 둔다.

### 3. 비밀번호·토큰 보관

- 비밀번호 해시는 라이브러리 기본(scrypt 계열) 사용. API 키는 해시 보관이 기본인지 구현 때 확인하고, 아니면 설정으로 켠다.
- 서버 비밀(세션 서명 키 등)은 k8s Secret 으로 주입, 저장소에 두지 않는다.

## 고려한 대안

| 대안 | 제외 이유 |
|---|---|
| 직접 구현 | 보안 실수 위험, 메일 인증·재설정·토큰 회전까지 공수 큼 |
| `oidc-provider`(완전한 OAuth/OIDC 서버) | 지금 필요한 범위(자체 가입·개인 토큰·장치 로그인)보다 훨씬 크고 가입·비밀번호 기능은 따로 필요 |
| Keycloak 등 별도 인증 서버 | pod·메모리 추가(4Gi 한도), PoC 에 과함 |
| Lucia | 유지보수 중단(학습 자료로 전환) |
| 로컬 앱 루프백 + PKCE | 동작은 같으나 앱이 로컬 포트를 열어야 하고 라이브러리 지원이 장치 인가보다 번거로움 |

## 결과

### C1 서버 1부 — 계정·프로젝트 (2026-10-20)

Better Auth **1.6.33**(`better-auth` · `@better-auth/api-key` · `@better-auth/drizzle-adapter` 같은 버전)으로 구현했다. 동작은 설치된 1.6.33 소스와 테스트로 확인했다.

| 필요 | 실제 구현 |
|---|---|
| 회사 도메인 가입 | `hooks.before`(`/sign-up/email`) + `databaseHooks.user.create.before` 두 곳에서 검사(대소문자 무시, 이메일 소문자로 저장). 거절 403 `EMAIL_DOMAIN_NOT_ALLOWED`. 허용 도메인 = `ALLOWED_EMAIL_DOMAINS`(필수 설정, 기본값 없음 — 2026-11-05 ADR-045) |
| 비밀번호 | 10~128자(`minPasswordLength`/`maxPasswordLength`), 해시는 라이브러리 기본(scrypt) |
| 메일 인증 | SMTP 가 있으면 `requireEmailVerification` · `sendOnSignUp` · `sendOnSignIn`(미인증 로그인 시 재발송) · 링크 24시간. nodemailer 10(로컬 Mailpit). 재설정 메일 1시간 |
| 관리자 승인 모드 | SMTP 미설정 시 자동. 가입하면 `status = pending`, `ADMIN_EMAILS` 계정만 바로 active. 승인 = active + emailVerified. 비밀번호 재설정은 관리자의 임시 비밀번호 발급(`POST /api/admin/users/:id/reset-password`) |
| 로그인 차단 | `databaseHooks.session.create.before` 에서 `status ≠ active` 면 403(`PENDING_APPROVAL` · `ACCOUNT_DEACTIVATED`) — 이메일 로그인과 장치 토큰 발급 모두 이 한 곳을 지난다 |
| 잠금 | 라이브러리 기능이 없어 직접: `hooks.after` 에서 401(비밀번호 틀림)만 세어 `login_attempts` 에 기록, 5회 → 10분 잠금(429 `ACCOUNT_LOCKED`, `hooks.before` 에서 거절). 성공 시 초기화. 미인증 403 은 세지 않음 |
| 세션 | 쿠키 7일 · 하루마다 연장 · httpOnly · SameSite=Lax · **cookieCache 끔**(비활성화·로그아웃 즉시 반영). 기본 내장 rate limit 은 설정값(`AUTH_RATE_LIMIT`) |
| 장치 인가 | `deviceAuthorization` — 코드 15분 · 폴링 5초 · `client_id` 허용 목록(`DEVICE_CLIENT_IDS`, 기본 `euta-app`) · 승인 주소 `<BASE_URL>/device`. 흐름: 코드 요청 → 브라우저(로그인 상태)에서 `GET /api/auth/device?user_code=` 로 **코드 확보** → `POST /device/approve` → 앱 폴링 → `access_token`(= 세션 토큰) → `bearer` 플러그인으로 API 호출 |
| 개인 토큰 | api-key 플러그인: 접두사 `euta_` + 48자, **해시 보관이 기본(SHA-256)** — DB 전체 덤프에 원문·본문 없음을 테스트로 확인. `start` 9자(`euta_`+4) 저장, `lastRequest` = 마지막 사용, 토큰당 분당 120회. 권한은 `permissions: { project: ['read'] | ['read','write'] }` |
| 토큰 관리 경로 | 발급·목록·폐기는 **`/api/me/tokens` 만**(만료 30·90·180·365일, 활성 10개 검사). 플러그인 자체 HTTP 경로(`/api/auth/api-key/*`)는 닫음. 토큰으로는 토큰 관리·관리자 API 불가(세션 필요) |
| 요청 인증 | 서버 자체 미들웨어 한 곳: `Bearer euta_…` → `verifyApiKey`, 그 밖 → `getSession`(쿠키·장치 토큰). 어느 쪽이든 사용자 `status = active` 확인. `enableSessionForAPIKeys` 는 끔 |
| 비활성화 | 한 트랜잭션에서 `status = deactivated` + 세션(웹·장치 토큰) · API 키 · 장치 코드 삭제. 다시 활성화해도 예전 토큰은 살아나지 않음 |
| 기타 | telemetry 끔. Better Auth 자체 로그는 `logger.log` 로 서버(Fastify/pino) 로그에 합류 — 같은 마스킹·같은 수집(평문 검사 대상). SMTP 미설정인데 `ADMIN_EMAILS` 가 비면 서버가 시작을 거부(승인할 사람이 없음). `/api/auth/*` 오류 응답에 euta 오류 봉투(`error: {code,message}`)를 덧붙임(라이브러리 필드 유지), RFC 8628 오류(`{error: "authorization_pending"}`)는 그대로 |

- ADR 과 달라진 점
  - `customAPIKeyGetter` 로 플러그인이 세션을 흉내 내게 하지 않고, 서버 미들웨어에서 `verifyApiKey` 를 직접 부른다(토큰 권한과 역할의 최소값 판정을 서버 한 곳에서 하기 위해).
  - 장치 인가는 승인 전에 **코드 확보 단계**(`GET /device?user_code=`)가 있다. 토큰 요청은 JSON 만 받는다(form 인코딩 415) — 로컬 앱(C2)은 JSON 으로 보낸다.
  - 1.6 API 키 테이블의 소유자 열은 `userId` 가 아니라 `referenceId` 다.
- 검증: auth 20 · tokens 10 · 권한(HTTP) 14 · 평문 검사 4건 포함 서버 테스트 90건 통과(Mailpit 실제 발송 1건 포함).
