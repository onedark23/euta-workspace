# ADR - 047 앱 업데이트 원본 선택

## 상태

구현 완료 (2026-11-09) — `feat/app-release`(앱 · 클라우드)를 새 이력 위로 옮기며 구현해 main 에 합쳤다(레포마다 커밋 하나, 작성자 noreply). 남은 것: 실제 GitHub 릴리스 1회 · 사내 미러 게시 · Windows · Linux 실기 확인(SPEC 완료 기준).

구현 메모

- 앱: `src/main/update-source.ts`(원본 고르기) · `AppUpdater` 의 `server` → `source()`(확인마다) · 백엔드 `setFeed` · 알림 경로 `latest*.yml` 해석(`yaml`) · `filesFromMeta`(맥 zip 옆 dmg) · 앱 설정 "받는 곳" · `scripts/release-github.mjs` · `publish: github` · `release:upload` 서버 주소 필수. `EUTA_UPDATE_SERVER` 는 연결 서버 대신 쓸 주소(개발 · E2E 전용).
- 클라우드: `GET /api/config` `appUpdates`(게시본 있음) · `k8s/example` 에 올리기 Ingress · `UPDATES_DIR` · `MIN_APP_VERSION`(회사 값은 사내 배포 레포). 웹 내려받기 화면의 "사무실 네트워크에서만" 문구 삭제(화면을 연 사람은 이미 서버에 닿아 있음).
- 검증: 클라우드 typecheck · 단위 351 · 웹 E2E 25(앱 내려받기 포함), 앱 typecheck · 단위 234 · update E2E 2(받는 곳 = 연결 서버, 알림 경로 dmg 주소, 업데이터 경로) + 화면 캡처 확인. `pnpm install --frozen-lockfile` 통과(클러스터 빌드 Job 이 씀).

## 맥락

- 2026-10-30 앱 배포 구현(ADR-041 · 042)은 업데이트 원본이 euta cloud 서버 하나였다 — 앱 코드 기본값이 그 서버 주소였고, 서명 없는 맥 알림은 서버의 `/api/app/releases` 를 읽었다.
- 2026-11-05 공개 전환(ADR-045): 공개 배포는 GitHub Releases, 클라우드 경로는 **미러로 유지**(사용자 결정). 공개 레포에는 특정 서버 주소를 넣지 않는다.
- 같은 앱 하나가 (a) 클라우드 없이 쓰는 사람, (b) 자기 조직 서버에 연결한 사람 모두에게 맞는 원본을 골라야 한다.

## 결정

1. **원본 두 곳, 앱이 고른다** — 앱에 클라우드 서버 주소가 있고 그 서버의 `GET /api/config` 가 `appUpdates: true` 면 그 서버(`/updates/<채널>/`), 아니면 GitHub Releases(`onedark23/euta-app`). 사내용 · 공개용 빌드를 나누지 않는다(사용자 결정 2026-11-09 — 권장안).
2. **`appUpdates` = 게시된 릴리스가 하나 이상** — 서버가 배포 기능은 있어도 아무것도 올리지 않았다면 GitHub 을 쓰게 한다(직접 구축한 서버가 업데이트를 막지 않게). 로그인 없이 읽는 `/api/config` 에 둔다(`microsoftLogin` 과 같은 자리).
3. **확인할 때마다 고른다** — 업데이터는 시작할 때 원본을 정하지 않고, 확인마다 서버 주소 · `appUpdates` 를 다시 읽는다. 원본이 바뀌면 electron-updater 의 피드 주소를 그때 바꾼다.
4. **넘어가지 않는다** — 클라우드를 골라야 하는데 서버(또는 `/api/config`)에 닿지 않으면 그 확인은 실패(조용히, 다음 확인 때 다시). 조직이 올린 버전 · `MIN_APP_VERSION` 과 다른 버전을 GitHub 에서 받아 섞이는 일을 막는다.
5. **두 원본 모두 generic 형식** — GitHub 도 electron-updater `github` provider 대신 generic provider 로 `https://github.com/onedark23/euta-app/releases/latest/download/` 를 읽는다.
   - 확인(Context7, electron-builder 26): `github` provider 는 `allowPrerelease` 일 때 Atom 피드에서 태그를 맞추고, 아닐 때 `releases/latest` 로 태그를 찾는다 — 태그 접두사(`tagNamePrefix`, 기본 `v`)와 prerelease 처리가 얽힌다. generic 은 기준 주소 + `latest*.yml` 만 보면 되고, 클라우드 경로와 코드가 같다.
   - `releases/latest/download/<이름>` 은 가장 최근 **정식(prerelease 아님)** 릴리스의 파일로 넘겨 준다(GitHub API 아님 — IP 당 횟수 제한 없음). 그래서 GitHub 릴리스는 prerelease 표시를 하지 않는다. 채널은 버전 이름이 담는다.
6. **서명 없는 맥 알림도 `latest-mac.yml`** — 원본에 상관없이 `latest-mac.yml`(yaml)을 읽어 버전 · 노트, 파일 목록에서 이 기기 arch 의 `.dmg` 를 고른다(Apple 칩에 arm64 가 없으면 Intel — 기존 `pickInstaller` 규칙). 서버의 `/api/app/releases` 는 웹 화면용으로 남는다.
7. **올리기** — GitHub: 앱 레포 `pnpm release:github`(GitHub CLI `gh release create app-v<버전>`, 노트 = `RELEASES.md` 그 절, 파일 전부, prerelease 아님, 레포 `onedark23/euta-app`). 클라우드 미러: 기존 `pnpm release:upload`, 서버 주소는 `--server` 또는 `EUTA_UPDATE_SERVER` 로 **반드시** 준다(기본값 없음). electron-builder `publish` 설정은 `github`(앱 안 `app-update.yml` 의 기본값 — 실제 피드는 앱이 확인 때 `setFeedURL` 로 정한다).

## 대안

- **사내용 빌드에만 회사 서버 주소를 넣기**(빌드 환경 변수): 단순하지만 사내 · 공개 빌드가 갈리고, 사내 빌드를 따로 올려야 한다.
- **클라우드 실패 시 GitHub 로 넘어가기**: 사무실 밖에서도 업데이트를 받지만, 조직이 아직 허락하지 않은 버전을 받아 최소 버전 · 서버 API 와 어긋날 수 있다.
- **electron-updater `github` provider**: 표준이지만 prerelease · 태그 접두사 처리가 버전 · 설정에 따라 달라지고(v26 → v27 `tagNamePrefix` 변경), 클라우드 경로와 코드가 둘이 된다.
- **사용자가 원본을 고르는 설정**: 고를 이유가 드물고, 잘못 고르면 최소 버전 잠금에 걸린다.

## 검증

- 단위(앱): 원본 고르기 4경우(서버 없음 · `appUpdates` 참 · 거짓 · 닿지 않음), 확인 중 원본 전환 시 피드 주소 바뀜, `latest-mac.yml` 해석(arch · Intel 대체 · 노트).
- 단위(서버): `/api/config` `appUpdates` — 게시본 없음 false · 게시 후 true · 초안만 false.
- 앱 E2E(가짜 업데이트 서버): 기존 auto · manual 두 경로가 원본 고르기를 거쳐서도 통과.
- 실제: GitHub 릴리스 1회(`0.1.0-alpha.1`) 후 클라우드 없이 실행한 앱이 GitHub 에서 감지.
