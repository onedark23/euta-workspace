# ADR - 016 프로젝트 저장소 구현

## 상태

채택 (2026-10-02, 구현). macOS(arm64)에서 단위 테스트와 E2E(개발 빌드 + 패키징된 앱)로 검증했다. 결과는 아래 "결과" 절.

## 맥락

- [SPEC_프로젝트-관리](SPEC_프로젝트-관리.md) 가 데이터 모델·저장 구조·화면을 확정했다. 이 ADR 은 SPEC 이 정하지 않은 **구현 세부**(메타데이터 형식, vault 형식, 파일 감시, IPC 모양, 화면 구조, 엔진 변경 범위)를 기록한다.
- 확인한 사실(2026-10-02)
  - Electron 44 `safeStorage`: `isEncryptionAvailable()` · `encryptString()` · `decryptString()` 는 동기, `getSelectedStorageBackend()` 는 **Linux 전용**(`basic_text | gnome_libsecret | kwallet* | unknown`). macOS 는 키체인 항목 `<앱 이름> Safe Storage` 의 키로 암호화한다(암호문 접두사 `v10`).
  - Chromium 스위치 `--use-mock-keychain` 을 주면 macOS 에서 실제 키체인 대신 테스트용 키를 쓴다 — 암호화·복호화 경로는 같고 키체인 항목이 생기지 않음을 확인(별도 이름의 시험 앱으로 `security find-generic-password` 0건).
  - 엔진 `run.json` 은 시작 때와 종료 때 두 번 쓰이고, `run.finished` 이벤트는 마지막 `run.json` 쓰기 **전에** 나간다 → 앱이 나중에 `run.json` 을 고쳐 쓰는 방식은 경합한다.
  - 엔진 `RunScript` 옵션에 디바이스 덮어쓰기가 없었고, MCP 도구 핸들러(`createEutaToolHandlers`)는 `ServerConfig` 를 생성 때 받아 호출마다 필드를 읽는다(`SecretGuard` 는 생성 시점 secrets 로 Redactor 를 만든다).
  - Node 24 `fs.watch(dir, { recursive: true })` 는 macOS·Windows 에서 동작한다(Linux 는 Node 20+ 지원이나 inotify 한도 영향).

## 결정

### 1. 저장 형식 — JSON 파일 (SQLite 아님)

```
<userData>/app.json                      { schema:1, recent:[id], lastProjectId?, aiModel }
<userData>/vault.json                    { schema:1, entries: { "<projectId>/<envId>/<NAME>": "<base64 ciphertext>" } }
<userData>/projects/<id>/project.json    Project (+ environments[] + suites[])
                        scripts/  baselines/<envId>/  runs/(+index.sqlite)  suite-runs/<id>.json  chats/<uuid>.json
                        activity/<YYYY-MM>.jsonl
```

- 프로젝트 메타데이터는 프로젝트당 JSON 1개. 크기가 작고(수 KB) 사람이 읽고 백업·복사하기 쉽다. 실행 색인은 엔진 형식(`runs/index.sqlite`) 그대로.
- 쓰기: 같은 폴더의 고유 임시 파일(`<file>.<pid>.<n>.tmp`, 권한 0600) → `rename`. 앱이 한 프로세스라 잠금은 두지 않는다.
- id: 10자 소문자 영숫자(`crypto.randomBytes`). 이름과 무관. 스위트 실행 id 는 12자.
- 읽을 때 정규화(`reviveProject`): 알 수 없는 필드 무시, 잘못된 env/suite 항목 버림, 깨진 `project.json` 은 그 프로젝트만 목록에서 빠진다.
- 입력 검증(main): 이름 1–80자, 주소는 `http(s)` 절대 URL·사용자정보 금지, 변수 키 `[A-Za-z_][A-Za-z0-9_]*` 이고 **자격증명처럼 보이는 키(`TOKEN`·`PASSWORD`·`API_KEY`… 엔진 MCP 와 같은 규칙)는 거부**(secret 으로 넣도록), 스크립트 경로는 `scripts/` 기준 상대·`..`/숨김 금지·`.yaml/.yml`.
- 옛 전역 데이터(`settings.json`·`runs/`·`chats/`)는 읽지 않고 지우지 않는다. 전역 `SettingsStore` 는 삭제했다.

### 2. vault

- 키 `projectId/envId/NAME`(이름 `[A-Za-z_][A-Za-z0-9_]{0,63}`), 값은 `safeStorage.encryptString()` 결과의 base64. 평문·해시·길이 정보를 남기지 않는다. 값 16 KiB 상한.
- `status()`: 암호화 불가 → 거부 사유, Linux 이고 백엔드가 `basic_text`/`unknown` → 거부. 거부면 `set()` 이 `VaultUnavailableError` 를 던지고 UI 는 경고 + 외부 파일 안내.
- 공개 메서드는 `set · remove · names · resolve · removePrefix · status` 뿐. **값을 이름으로 돌려주는 getter 가 없다**(테스트로 단언). `resolve()` 는 main 의 실행 조립에서만 호출한다. 복호화 실패 항목은 이름만 보고("다시 입력하세요").
- IPC 는 쓰기 전용: `secret:set(projectId, envId, name, value)` 의 반환은 **이름 목록**. 렌더러 입력란은 저장 직후 비운다.
- 환경 삭제 = 그 환경 항목 삭제, 프로젝트 삭제 = 접두사 전체 삭제.
- 환경별 **외부 secrets 파일** 선택 가능(`Environment.secretsFile`, 절대 경로). 지정하면 vault 대신 그 파일만 쓴다(합치지 않음 — 출처를 하나로 두어 어느 값이 쓰였는지 분명하게). 파일은 AI `read_file` 로 읽을 수 없다(ADR-015 규칙 유지).
- 렌더러로 가는 `ProjectView` 의 환경에는 `secretNames` 와 출처(`vault|file`)만 있다.

### 3. 실행 조립과 엔진 변경 (최소)

- `run-options.ts`(순수 함수): `env = process.env − 앱 내부 토큰 + BASE_URL(환경 주소) + 환경 vars + 실행별 덮어쓰기`, `secrets = vault 또는 파일`, `runsDir = <프로젝트>/runs`, `baselineDir = <프로젝트>/baselines/<envId>`, 브라우저 = 프로젝트 기본값(실행별 선택이 우선), `meta = { projectId, projectName, envId, envName (+ suiteRunId, suiteName | source: 'ai') }`. 환경이 없으면 BASE_URL·baselineDir 를 넣지 않는다.
- 엔진 변경 2건(엔진 레포 커밋, 기존 134 테스트 그대로 + 1):
  1. `BaseRunOptions.meta` → `run.json` 의 `meta` 객체(시작·종료 기록 모두). `ServerConfig.runMeta` 를 `run_script`·`session_open` 에 전달. SPEC "run.json 에 프로젝트 id·환경 이름" 을 그대로 지키는 유일하게 경합 없는 방법(앱 사후 패치는 위 확인 사실 때문에 불안정, 별도 파일은 SPEC 과 다름). 추가 필드라 기존 형식은 유지된다.
  2. `BaseRunOptions.browserDevice`(browser.device 덮어쓰기) + `ServerConfig.runBrowser`(도구 입력에 browser 가 없을 때의 engine/device 기본값). 프로젝트 기본 디바이스를 앱 실행과 AI 실행에 똑같이 적용하기 위함.
- History 의 환경 열은 `run.json` 앞부분(16 KiB)에서 `meta` 만 읽어 run 디렉터리별로 캐시한다(실행 중인 run 은 읽지 않음).

### 4. 스크립트 라이브러리 · 파일 감시

- 목록: `scripts/` 재귀(깊이 8, 2,000개, 숨김·`node_modules` 제외), 이름은 `name:` 줄, 최근 실행은 `index.sqlite` 의 `scriptPath` 기준 최신 1건.
- 가져오기·새로 만들기는 덮어쓰지 않고 `이름-2.yaml` 처럼 빈 이름을 고른다. 이름 변경·삭제는 스위트의 스크립트 참조도 고친다.
- 감시: 프로젝트를 열 때 `fs.watch(scripts, { recursive: true })` 1개(250ms 디바운스). 앱 자신의 조작은 2초 동안 "자기 변경"으로 표시해 중복 기록하지 않는다. 바깥 변경은 이전 목록과 비교해 `script.created / deleted / changed` 로 기록하고 렌더러에 `scripts:changed` 를 보낸다. 행위자는 그 프로젝트 채팅이 응답 중이면 `ai`, 아니면 `user`(추정 — 외부 편집기와 AI 저장을 파일 이벤트로 구분할 수 없어서). 감시가 불가능한 환경이면 조용히 끄고 목록은 탭을 열 때 갱신된다.
- 열기 = `shell.openPath`(기본 편집기), 내보내기 = 저장 대화상자 → 복사. 가져오기 대화상자는 main 이 연다(렌더러가 임의 경로를 넘기지 않음).

### 5. 스위트

- 직렬 실행. 항목마다 `startRun(…, actor 'suite', meta.suiteRunId)`. 결과 상태 = 실행된 항목의 최악값(`error > failed > passed`), 아무것도 안 돌았으면 `error`. 실패 시 중단이면 다음부터 `skipped`.
- 취소 = 플래그 → 진행 중 스크립트는 끝까지, 나머지 `skipped`, `cancelled: true`.
- `suite-runs/<id>.json` 을 시작·항목 시작·항목 종료·끝에 원자적으로 다시 쓴다. 앱이 도중에 종료되면 다음 로드 때 `running/pending` 을 `skipped` 로 닫고 `interrupted: true`.
- 같은 프로젝트에서 동시에 스위트 1개만(입력·화면 점유 충돌 방지).

### 6. 작업 로그

- 줄 단위 `appendFileSync`(권한 0600), 월 파일은 이벤트 시각(로컬)의 `YYYY-MM`. 읽기는 최신 월부터 거꾸로, 깨진 줄은 건너뛴다. append·list 는 예외를 밖으로 던지지 않는다.
- 요약은 500자, 줄바꿈 제거, 그리고 **프로젝트의 모든 secret 값으로 마스킹**(엔진 `Redactor` — URL 인코딩 등 변형 포함)한 뒤 기록. 호출하는 쪽도 값을 넣지 않는다(`secret.set` 은 이름만).
- run 기록은 LiveStore 의 수명주기 훅(`run.started`/`run.finished`, 실시간 이벤트만 — History 재생은 제외, runId 별 1회)에서 남긴다. 그래서 앱·스위트·AI·외부 MCP 실행이 한 경로로 기록된다. 행위자/환경은 앱이 시작한 run 이면 내부 표(runId → user/suite/ai + 환경)에서, 아니면 출처(`mcp`)에서.
- `chat.started` = 첫 사용자 메시지 때, `chat.turn` = 턴 종료 때 "요청 첫 120자 · 도구: <euta 도구 이름>".
- 종류 매핑: 이름·설명·고정 → `project.updated`, 기본 브라우저·기본 환경·앱 AI 모델 → `settings.changed`.

### 7. AI 채팅

- `ChatStore(<프로젝트>/chats)` 를 프로젝트마다, `ChatEngine` 도 프로젝트마다(처음 쓸 때 생성). 프로젝트를 바꿔도 다른 프로젝트의 턴은 계속 돈다.
- 채팅에 `projectId`·`envId` 저장(새 채팅 = 프로젝트 기본 환경). 작업 폴더 = 프로젝트 `scripts/`(고정, "변경…" 없음).
- `ChatEngine` 은 턴마다 `context(chat)` 를 받는다: `ServerConfig`(위 조립) + 작업 폴더 + 프로젝트 요약 + **설정 해시 key**. key 가 바뀌면(환경 전환, 환경 주소·변수·secret 변경) 다음 턴 전에 도구를 다시 만든다 — 그 채팅이 연 AI 브라우저 세션은 닫힌다. 같은 설정이면 도구(세션)를 턴 사이에 유지한다. → ADR-015 의 공백 "채팅 중 설정 변경은 새 채팅부터" 를 해소. 엔진의 "config getter" 변경 없이 해결.
- 시스템 프롬프트에 프로젝트 이름·환경 목록(이름·주소)·선택 환경·secrets **이름** 추가.
- 응답 중에는 환경을 바꿀 수 없다(UI 비활성 + main 거부).

### 8. IPC · 화면 구조

- 프로젝트별 호출은 모두 **projectId 를 명시**한다(`scripts:list(projectId)` · `history:list(projectId)` · `ai:chats(projectId)` …). main 의 "현재 프로젝트"는 고급 터미널의 `EUTA_RUNS_DIR` 와 앱 설정 변경 기록에만 쓴다(`project:open` 이 정함, 프로젝트가 없으면 터미널 실행 거부).
- 이벤트: `project:changed` · `scripts:changed(projectId)` · `suite:update(SuiteRun)` · `activity:appended(projectId, e)` · `ai:chat-update(projectId, chat)` · `live:update`(전역).
- `ProjectService`(Electron 비의존, `safeStorage` 주입)가 저장소·vault·로그·라이브러리·실행·스위트·채팅을 묶고, `index.ts` 는 IPC 매핑만 한다 → 단위 테스트가 서비스를 직접 시험.
- LiveStore 는 전역 1개. run 에 `projectId` 를 붙인다(앱/AI 실행은 등록 때, MCP·History 는 run 디렉터리가 `projects/<id>/runs/` 아래인지로 판단). Live 탭은 현재 프로젝트 + 프로젝트 없는 외부 실행을 보이고, 사이드바는 프로젝트별 실행 중 개수를 표시한다.
- 렌더러: 왼쪽 사이드바(고정 → 최근 순, 새 프로젝트, 앱 설정) + 프로젝트 화면(`key=projectId` 로 다시 마운트, 프로젝트 안에서는 탭 마운트 유지). 첫 실행이면 안내 + 만들기 폼. 탭: 스크립트 · Run(스크립트·환경 선택 + 스위트 실행) · Live · History(환경 열, 스위트 묶음 접기/펴기) · AI · 작업 로그(종류·행위자 필터, 클릭 → run/채팅/스크립트) · 프로젝트 설정(기본 정보·환경·secrets·기본 브라우저·스위트·삭제). 앱 설정은 AI 기본 모델·vault 상태·데이터 위치만.
- 프로젝트 삭제: 이름을 입력하는 앱 안 확인창(네이티브 대화상자 대신 — E2E 로 검증 가능). 실행 중 run·스위트·응답 중 채팅이 있으면 거부하고 이유를 보인다.
- 프로젝트를 바꾸면 그 프로젝트 화면이 다시 마운트되므로, 고급 터미널의 pty 는 닫힌다(새 터미널은 새 프로젝트의 `EUTA_RUNS_DIR` 로 뜬다).

### 9. 테스트 전용

- `EUTA_E2E=1` 일 때만 `app.commandLine.appendSwitch('use-mock-keychain')` — 자동 테스트가 사용자 키체인에 항목을 만들거나 권한 대화상자를 띄우지 않게. 일반 실행에는 없다.
- E2E 는 main 의 `dialog.showOpenDialog` 를 `electronApp.evaluate` 로 바꿔 가져오기 대화상자를 대신한다.

## 이유

- JSON + 원자적 rename 은 의존성 0, 손상 범위가 파일 하나, 사람이 읽을 수 있다. 실행 색인처럼 질의가 필요한 데이터는 이미 SQLite 다.
- vault 를 앱 전역 파일 하나로 둔 것은 SPEC 대로 — 프로젝트 폴더를 통째로 복사해도 secret 은 따라가지 않는다(의도된 성질).
- run.json `meta` 는 엔진이 쓰는 순간에 함께 들어가 경합이 없고, 외부 도구(리포트·CLI)도 같은 파일에서 읽을 수 있다.
- 서비스 계층을 Electron 에서 떼어 두면 vault 거부·스위트·로그·재시작 복원을 픽스처 사이트로 빠르게(수십 초) 검증할 수 있다.

## 고려한 대안

| 대안 | 제외 이유 |
|---|---|
| 프로젝트 메타데이터를 SQLite 로 | 스키마 이전·바인딩 관리 부담, 작은 문서에 과함. 질의 수요 없음 |
| vault 를 프로젝트 폴더 안에 | 폴더 복사·백업에 암호문이 따라감(다른 PC 에선 복호화 불가해 쓸모도 없음). SPEC 은 전역 1개 |
| 키체인에 항목을 secret 마다 직접 저장 | 플랫폼별 구현·권한 대화상자 증가. `safeStorage` 가 Electron 표준 |
| `basic_text` 에서도 저장(경고만) | SPEC "저장 거부". 평문 수준 저장소에 secret 을 두지 않는다 |
| 실행 메타를 앱이 run.json 에 사후 패치 | 엔진의 마지막 쓰기와 경합(위 확인 사실) |
| 실행 메타를 별도 `app-meta.json` | SPEC 과 다름 + 다른 도구가 모름 |
| 엔진 `ServerConfig` 를 getter 로 바꿔 채팅 중 환경 전환 | 엔진 API 변경이 커짐. 도구 재생성으로 충분(세션이 닫히는 대가는 문서화) |
| chokidar 로 감시 | 의존성 추가. Node 내장 recursive watch 로 충분 |
| 네이티브 확인 대화상자로 프로젝트 삭제 | 자동 검증 불가, 이름 입력 확인이 실수 방지에 더 강함 |

- **남은 공백(알려진 한계)**
  - 스크립트 변경의 행위자(user/ai)는 추정이다(4절).
  - Linux 에서 recursive watch 는 inotify 한도에 걸릴 수 있다(Windows·Linux 는 코드만, 검증은 macOS).
  - 진행 중인 run 은 취소할 수 없다(엔진 중단 API 없음) — 스위트 취소도 남은 스크립트만 건너뛴다.
  - 키체인이 초기화되는 등으로 복호화가 안 되면 그 secret 은 다시 입력해야 한다(이름만 알려 줌).
  - 앱 안 스크립트 편집기는 SPEC 범위 밖(외부 편집기 또는 AI 채팅).
  - 실제 키체인은 자동 테스트가 다루지 않는다(mock keychain). 첫 실사용 때 키체인에 `euta Safe Storage` 항목이 생기고, `pnpm package` 로 다시 빌드한 앱(새 ad-hoc 서명)은 그 항목 접근을 한 번 물을 수 있다 — "항상 허용" 하면 된다.
  - 개발 실행(`euta-app`)과 패키징 앱(`euta`)은 앱 이름이 달라 userData 폴더와 키체인 키가 다르다. 한쪽의 `vault.json` 을 다른 쪽으로 옮기면 복호화되지 않는다(이름만 남고 "다시 입력하세요").
