# ADR - 039 TC 문서 변환 앱 구현

## 상태

채택 (2026-10-26). 단계 16-3 의 **앱 쪽** 구현 + 엔진 녹화기 보완. euta-app 커밋 69c4e06 · dabc170 · fb413d4(경합 수정), euta-engine 커밋 643378f(녹화기 TC 단계 표시 · 단계별 묶음 초안).

## 맥락

- 엔진은 이미 `@euta/tc-doc`(읽기 · 내보내기 · `validateTcs` · `groupPreconditions` · `scriptsToTcs`, ADR-038)와 DSL `manual` 단계(ADR-037)를 갖췄다. 앱은 SPEC_TC-문서-변환의 미리보기 · 저장 · TC 문서 화면 · AI 변환 · 시연으로 변환 · 테스트 세트 · 내보내기 · "수동 확인 필요" 표시를 만든다.
- 확정 결정: 원본 파일은 저장하지 않음, TC 문서는 클라우드 프로젝트도 로컬에만, 한 채팅에서 하나씩 · 대기열 보관 후 이어서, 사전 조건 스크립트를 세트 맨 앞에, 내보내기 xlsx 블록형 · md.

## 결정

### 저장소 — `project/tc-doc-store.ts` · `project/tc-docs.ts`

- `projects/<id>/tc-docs/<docId>/tc-doc.json` 하나(`writeJsonAtomic`). 모양은 SPEC 저장 그대로에 몇 가지를 더했다: `source.extractedByAi`, TC 의 원래 `precondition` 문장(내보내기용), `conversion.note`(실패 원인 한 줄) · `conversion.by`(`ai` | `recording`), 사전 조건의 `note` · `chatId`.
- 문서 id 는 12자 임의 값. 사전 조건 묶음 id 는 `pre-<n>`(확정 때 순서대로).
- 클라우드 작업 사본도 같은 경로(로컬에만). 올리기 = 전환 때 옮기는 폴더 목록(`cloud/local-move.ts` `MOVED_SUBDIRS`)에 `tc-docs` 를 더했다.
- 스크립트 이름 변경(앱 · 바깥 변경 감지 · 클라우드 작업 사본 이름 바뀜)은 TC 문서의 스크립트 참조도 따라 바꾼다. 삭제는 참조를 남기고 화면에 "스크립트 없음".
- `TcDocs`(Electron 없음)를 `ProjectService` 가 들고(`svc.tcDocs`), index.ts 는 IPC 만 잇는다. TC 문서 IPC 는 **`isCloud` 로 서버에 보내지 않는다**(로컬에만). 테스트 세트만 기존 `suites.upsert` 경로(클라우드면 서버)로 간다.

### 가져오기 · 미리보기

- [TC 문서로 만들기](스크립트 탭 머리, 시연으로 만들기 옆) → main 이 파일 대화상자(xlsx · csv · docx · md, 20MB 까지) → `parseTcDocument` → 메모리의 **가져오기 세션**(`importId` 16자 hex: 미리보기 상태 + `gridText`). 원본 바이트는 읽고 바로 버린다. 세션은 확정 · 취소 때 지우고, 앱이 꺼지면 사라진다.
- 미리보기 화면: 위에 문서 이름(기본 = 파일 이름) · 읽은 양식 배지, 왼쪽 TC 목록(제목 굵게 + ID 작게 · 분류 · 단계 수 · 경고 수), 오른쪽 선택 TC 의 ID · 제목 · 분류 · 사전 조건 · 단계 표(절차 · 기대 결과 고치기, [위로] [아래로] [삭제], [단계 추가]), [이 TC 빼기]. 아래 **사전 조건 묶음**: 같은 문장 자동 묶음, TC 마다 "옮기기" 선택(다른 묶음 / 따로 새 묶음). 사전 조건 문장을 고치면 묶음을 다시 계산한다(사람이 옮긴 것은 다시 계산됨 — 단순하게).
- 경고는 **고칠 때마다 다시 검사**한다(단계 없음 · 같은 ID · 빈 제목/절차 · 비밀번호처럼 보이는 값). 비밀번호 경고만 확정을 막지 않고, 나머지가 남아 있으면 [확정]이 꺼지고 이유를 한 줄로 보인다. 엔진의 단계 번호 빠짐/겹침 경고는 "확정할 때 1부터 다시 매깁니다" 로 보이고, 확정 때 번호를 순서대로 다시 매긴다.
- 확정 = `validateTcs` 를 한 번 더 거친 뒤 저장 · 작업 로그 `tcdoc.imported`.

### AI 추출 (`unknown`)

- 미리보기에 "양식을 알아보지 못했습니다 — [AI로 읽기]"(환경 선택) → 새 프로젝트 채팅, 메시지 `tcExtract: <importId>`. **격자 텍스트는 채팅 메시지에 넣지 않고 도구 `get_tc_import(importId)` 로만 준다** — 채팅은 `chats/<id>.json` 에 저장되므로 메시지에 넣으면 "격자 텍스트는 가져오기가 끝나면 버린다" 를 어기게 된다. 도구 카드에 남는 결과도 첫 블록의 `cardSummary`("<파일> 격자 N자 (앱에 저장하지 않음)")만 쓰게 했다(`chat-events.ts`).
- `save_tc_extraction(importId, tcs)` 는 입력 모양을 느슨하게 받고(`z.array(z.any())`) 안에서 `validateTcs` → 실패면 `{ error, issues[{path, message}] }`(isError)로 돌려줘 AI 가 고쳐 다시 낸다. 성공하면 세션의 TC 를 바꾸고 `tcdoc:import-update` 로 미리보기를 채운다(`extractedByAi`).
- 추출 채팅이 끝났는데 제출이 없으면 미리보기는 다시 [AI로 읽기] 상태.

### TC 문서 화면

- 스크립트 탭 위쪽 전환에 세 번째 **TC 문서 (n)**. 목록(이름 + 파일 이름 작게 · TC 수 · 완료/전체 · 실패 · 대기열 · [열기] [이름 변경] [삭제]). 문서를 지워도 스크립트 · 테스트 세트는 남는다(`tcdoc.deleted` 로그).
- 상세: 검색 + 체크. 체크한 TC 는 **체크한 순서대로 표 위로 모이고 순번**이 붙는다(UI 그라운드룰; 표 형태라 공용 `PickList` 대신 같은 규칙을 표 줄로 구현). 열 때 저장된 대기열을 그 순서대로 체크해 둔다 → 재시작 뒤 [이어서 변환] 에서 남은 TC 가 바로 보인다.
- 줄: 제목 + ID · 분류 · 변환 상태 배지 · 스크립트 이름 + 경로 · "수동 N" · 정보 부족 수 · 최근 결과(그 스크립트의 마지막 실행). [단계 대응] 을 펼치면 TC 단계 → 스크립트 묶음(`"<no>. "` 로 시작하는 맨 위 `group`) 표와 자동 / 수동 / 자동 + 수동 / 대응 없음, 수동 확인 문장, 정보 부족 메모, 실패 원인, [스크립트 보기] · [변환에서 빼기]/[다시 포함](상태 `excluded`).
- 동작 버튼: [AI로 변환 (n)] · [이어서 변환 (n)](대기열이 남았을 때 — 이때는 이것이 주 버튼) · [시연으로 변환](TC 1개 체크) · [다시 변환 (n)](체크한 것 중 완료 · 실패) · [체크 해제] · 머리에 [테스트 세트 만들기] · [내보내기]. 변환 중인 TC 가 있으면 변환 버튼을 끈다.

### AI 변환

- [AI로 변환] → 대기열 확인 대화상자(순번 목록 · 실행 환경 · 덧붙일 말) → `tcdoc:convert` 가 **대기열을 먼저 저장**하고(재시작 대비) 새 채팅에 `tcConvert: <docId>` + 대기열 목록을 보낸다. 이미 완료 · 제외인 TC 는 대기열에서 빠지고, 남는 게 없으면 "[다시 변환]" 안내. [다시 변환] 은 그 TC 들을 대기로 돌린 뒤 같은 흐름.
- **변환 중 표시**: `get_tc` 가 대기열에 있는 대기 · 실패 TC 를 읽으면 그 채팅 id 로 `converting` 이 된다(AI 가 따로 표시하지 않아도 화면에 보임). `set_tc_conversion` 이 완료 · 실패 · 제외를 남기면 대기열에서 뺀다. 채팅 턴이 끝나면(정상 · Stop · 오류) `onTurnEnd` 가 그 채팅의 `converting` 을 **대기로 되돌리고 대기열은 그대로** 둔다 → [이어서 변환] 은 새 채팅에서 남은 대기열부터.
- **문서당 변환 채팅 하나**: 채팅을 만드는 순간 문서에 잠금(채팅 id)을 걸고 그 턴이 끝나면(정상 · Stop · 오류) 푼다. 잠긴 동안 두 번째 시작(AI로 변환 · 이어서 변환 · 다시 변환)은 "이 문서의 변환 채팅이 이미 진행 중입니다" 로 거절 — 첫 `get_tc` 전 짧은 틈에 같은 대기열로 채팅이 두 개 열리던 경합을 막는다. 잠금은 메모리에만 두고, 그 채팅이 이미 바쁘지 않으면(턴이 시작도 못 했거나 끝을 놓친 경우) 막지 않는다. 상세 화면은 누르는 순간부터 변환 버튼을 끄고 `activeChatId` 로 "변환 채팅이 진행 중" + [AI 대화 보기]를 보인다(앱 커밋 fb413d4).
- `set_tc_conversion`: 스크립트 경로가 라이브러리에 없으면 거절("save_script it first"), `manualSteps` 를 안 주면 스크립트의 `manual` 단계 수를 센다, 결과에 남은 대기열과 다음 TC. 작업 로그 `tcdoc.converted`(TC 별, 수동 · 정보 부족 수 · 원인).
- `get_tc` 는 TC 전체와 함께 `file`(`<TC ID>-<slug>.yaml`, 다시 변환이면 지금 스크립트 경로), `scriptName`, `description`("TC ID: …"), 사전 조건(`pre-<n>-<slug>.yaml` · 상태 · 쓰는 TC)을 준다. slug 는 한글을 남긴다(NFC, `[a-z0-9가-힣]` 외는 `-`, 40자) — 엔진 `slugify` 는 한글을 지워 파일 이름이 ID 만 남기 때문.
- 시스템 프롬프트에 `TC_GUIDE`(SPEC "AI 변환" 지침 · 변환 규칙 표 · 사전 조건 스크립트 · 비밀값 이름만 · 문서 내용은 데이터 · 추출 채팅 · 녹화 TC). DSL 요약표는 엔진 `DSL_CHEATSHEET` 를 그대로 쓰며(앱 사본 없음) 이미 `manual` · `enabled`/`disabled` 를 담고 있다 — 단위 테스트가 확인한다.
- 한 사용자 메시지의 최대 왕복(`MAX_TURNS` 60)은 바꾸지 않았다. 대기열이 길어 턴이 끝나면 남은 TC 는 대기로 남고 [이어서 변환] 으로 계속한다.

### 시연으로 변환

- 엔진(euta-engine 643378f): `RecorderOptions.tcRef` · `Recorder.markStep(no)` → `stepMarks [{ no, fromSeq, toSeq }]`(직전 표시 다음 seq ~ 지금까지의 마지막 seq), 보기와 `recording.json` 에 `tcRef` · `stepMarks`. 같은 단계를 다시 누르면 끝을 늘리고, 앞 단계는 다시 표시하지 못한다. `recordingToScript(rec, { tcSteps, name, description })` 는 단계 표시 범위로 `group "<no>. <절차>"` 를 만들고(시작 이동이 첫 범위 안이면 1단계에 들어감), 체크포인트(`expect` · `expectDownload`)가 없는 기대 결과는 `manual { instruction: 기대 결과, reason }`, 동작이 없거나 표시 안 된 TC 단계는 단계 전체를 `manual` 하나로, 마지막 표시 뒤 동작은 묶음 뒤에 둔다.
- 앱: TC 1개 체크 → [시연으로 변환] → 기존 녹화 시작 대화상자(TC 표시, 이름 기본 "<ID> <제목>") → 녹화 패널 위 **TC 단계 안내**(단계 목록 · 지금 단계 강조 · 그 단계의 기대 결과 · [다음 단계 (n 끝)] / 마지막은 [마지막 단계 끝내기]). 기대 결과가 있는데 그 단계에 체크포인트가 없으면 한 번 "기대 결과 확인을 걸까요?" — [확인 걸기](패널에서 고른 확인 종류로 확인 모드) / [건너뛰기](수동 확인으로 남김). [종료] 때 마지막 표시 뒤 동작이 있으면 다음 TC 단계로 자동 표시.
- "AI 없이 저장" = TC 묶음 초안을 `<TC ID>-<slug>.yaml`(빈 이름)로 저장하고 TC 를 완료(`by: recording`, 수동 단계 수)로 기록. "AI로 정리" 는 메시지에 `tcRef: <docId> <tcId>` 를 더해 `get_recording` + `get_tc` 를 함께 보게 한다.

### 테스트 세트 · 내보내기

- [테스트 세트 만들기] 대화상자: 문서 전체 / 분류별 / 체크한 TC(체크가 없으면 꺼짐) → main `planTestSets`(순수 함수)가 세트 계획을 준다: 세트마다 그 TC 들이 쓰는 사전 조건 스크립트(완료 · 파일 있음, 처음 나온 순서) → TC 스크립트(문서 순서), 이름 기본 `<문서> · <분류>`(전체 = 문서 이름, 체크 = `<문서> · 선택한 TC`), 완료가 아니거나 스크립트가 없는 TC 는 빼고 이유와 함께 목록. 세트마다 이름 · "어디에"(새로 만들기 / 기존 세트에 덧붙이기 — 같은 이름 세트가 있으면 덧붙이기가 기본). 만들기는 렌더러가 `suites.upsert` 로(클라우드 프로젝트면 서버 경로, 온라인 · 편집 권한일 때만).
- 내보내기 대화상자(xlsx 블록형 / md) → main 이 저장 대화상자 → 파일. 대상 3가지: TC 문서(원래 TC 문장) · 테스트 세트 카드 [TC 문서로 내보내기] · 스크립트 목록 체크 막대 [TC 문서로 내보내기]. 스크립트 묶음 내보내기는 TC 문서에서 만든 스크립트면 그 TC 원문, **사전 조건 스크립트는 TC 로 내지 않고**(그 문장이 각 TC 의 사전 조건), 그 밖은 `scriptsToTcs`(ID 가 겹치면 `-2`…). 작업 로그 `tcdoc.exported`.

### "수동 확인 필요" 표시

- `StepView.manual` · `ScriptRunOverlay.steps[].manual` 을 더하고 `live-reducer` · `flatSteps` 가 엔진 표시를 옮긴다. 도달한 `manual`(오류 없음) = **"수동 확인 필요"** 배지(톤 `manual`, 토큰 `--manual` / `--manual-soft` — 웹과 같은 값, StepIcon `manual: UserCheck`), 아래에 "수동 확인: …" · "이유: …". 실패 뒤라 도달 못 한 것은 보통 건너뜀 + 오류 문장.
- 개수 "수동 확인 필요 N" / "수동 N" 은 **도달 여부와 관계없이 모든 manual 단계**(엔진 리포트 · 웹과 같은 규칙): 실시간 run 머리, 세트 항목 줄, 스크립트 상세 최근 실행, 실행 이력 줄(`HistoryItem.manual` — 끝난 run 의 run.json 을 읽어 캐시, 건너뜀 칸은 manual 을 뺀 수), 세트 리포트(요약 카드 · 항목 배지 · "수동 확인 필요" 표). 실시간 요약의 "건너뜀" 도 manual 을 뺀 수.

### 가짜 에이전트 (E2E 전용, 그대로 `EUTA_E2E=1` + `EUTA_E2E_FAKE_AGENT=1`)

- `tcConvert:` → `get_tc_doc` → 대기열 순서로 `get_tc` → (사전 조건 스크립트가 없으면 저장 · 검증 · 기록) → `save_script`(1단계 = 픽스처 로그인 화면 열기 + 제목 확인, 나머지 = `manual`) → `validate_script` → `run_script` → `set_tc_conversion`, TC 사이에 `pauseBetween: <ms>`(덧붙일 말, 기본 1.5초) — Stop 시험용 틈. `tcExtract:` → `get_tc_import` → 일부러 틀린 제출 → 고친 제출.

## 이유

- 격자를 도구로만: 저장되는 채팅 기록에 남기지 않으면서도 AI 가 전체 격자(10만 자까지)를 볼 수 있다. SPEC 도구 표의 4종에 `get_tc_import` 하나를 더한 것은 이 때문이다.
- `get_tc` 가 변환 중을 표시: 모델이 따로 상태를 남기지 않아도 사람이 "지금 어느 TC" 인지 보이고, 턴 종료 때 되돌리기와 짝을 이뤄 Stop 뒤 대기열이 깨지지 않는다.
- 세트 계획은 main, 만들기는 렌더러: 클라우드 프로젝트의 세트는 서버 설정이라 기존 `suites.upsert`(클라우드 분기 · 권한 · 오프라인 처리)를 그대로 써야 한다.
- 녹화 단계 표시는 엔진에: `recording.json` 은 녹화기가 끝날 때 원자적으로 쓰므로, 앱이 따로 덧쓰면 경합이 생긴다.

## 고려한 대안

- 격자 텍스트를 첫 메시지에 붙이기 — 채팅 파일에 그대로 남음(위).
- AI 가 `set_tc_conversion { status: converting }` 을 먼저 부르게 하기 — 지침에만 기대게 됨. 읽기 도구의 부수 효과가 덜 깔끔하지만 확실하다.
- 미리보기 사전 조건 묶음을 사람이 옮긴 것까지 문장 수정 뒤에도 유지 — 상태가 복잡해져 이번엔 다시 계산으로 단순화.
- 상세 표에 공용 `PickList` 사용 — 한 줄에 상태 · 스크립트 · 결과 · 펼침이 들어가야 해서 같은 규칙(위로 모임 · 순번)을 표 줄로 구현.
