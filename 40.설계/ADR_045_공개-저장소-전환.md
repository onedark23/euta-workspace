# ADR - 045 공개 저장소 전환

## 상태

진행 중 (2026-11-06). **1 ~ 5 완료**(아래 "진행 기록") — 다섯 레포가 `github.com/onedark23/` 에 공개됐다. 남은 것은 6(앱 업데이트를 GitHub Releases 로, `feat/app-release`).

## 맥락

- PLAN 결정 "공개 · 소유": euta 를 개인 제품으로 개인 GitHub 에 공개(Naby 와 같은 전략, 라이선스 없음), 회사는 같은 소스로 사내 서버를 직접 운영, 제품 문서는 GitHub · 회사 내용은 Confluence, 앱 업데이트는 GitHub Releases(서명 없이 시작).
- 코드는 이미 설정으로 동작해 회사 값이 적다(2026-11-05 확인): 엔진 · 플러그인 0곳, 클라우드는 `k8s/dev` · `.env.example` 뿐, 앱은 예전 회사 이름이 든 `appId` 와 테스트 메일 주소. 다섯 레포의 전체 이력에 비밀 파일 · 토큰 형태 문자열은 없다.
- 그러나 이력에는 회사 배포 값(Entra 테넌트 ID · 사무실 IP 허용 목록 · 사내 이미지 저장소 · 사내 도메인)이 남아 있다.

## 결정

1. **회사 배포 설정 분리** — `euta-cloud/k8s/dev`(ConfigMap · kustomization 이미지 · ingress 허용 목록 · `create-secrets.sh` · README) 를 사내 배포 레포(비공개 Bitbucket)로 옮긴다. GitHub `euta-cloud` 에는 회사 값이 없는 예시(`k8s/example`, 자리 표시 값)만 둔다. ArgoCD 는 회사 레포를 본다. 사내 이미지는 회사가 GitHub 의 태그(버전)로 빌드해 사내 저장소에 올린다 — 지금 방식 그대로, 소스 위치만 바뀐다.
2. **회사 흔적 정리** — `.env.example` 의 회사 도메인 → `example.com`. 테스트 · E2E 의 회사 도메인 메일 → `@example.com`(RFC 2606 예시 도메인). 앱 `appId` 는 **`dev.euta.app`**(Naby `dev.naby.app` 과 같은 방식, 사용자 결정 2026-11-05)으로 바꿨다 — 데이터 폴더(`~/Library/Application Support/euta`)와 safeStorage 키체인 항목(`euta Safe Storage`)은 번들 ID 가 아니라 앱 이름 `euta` 를 따르므로 기존 데이터를 그대로 읽는다(패키징 빌드로 번들 ID · ad-hoc 서명 확인). 번들 ID 에 묶인 것은 `~/Library/Preferences/<id>.plist`(대화상자 크기 같은 macOS 기본값)뿐이고, Windows 설치 ID 는 아직 배포 전이라 영향 없음.
3. **문서 나누기** — `euta-workspace` 문서를 제품 문서(SPEC · ARCH · ADR · DSL 규격 · 제품 PLAN)와 회사 내용(실사용 대상 서비스 TC · 사내 운영 · 회의록 · 보고 · 사람 이름이 든 기록)으로 분류한다. 제품 문서는 회사 내용을 덜어내 GitHub 에, 회사 내용은 사내 문서(Confluence, 비공개) 로(pdoc `confluence_sync.py`, 발행은 사용자 확인 후). 회사 내용을 담은 로컬 문서는 `.gitignore`.
4. **새 이력** — 레포마다 정리를 마친 작업 트리로 이력 없는 첫 커밋을 만들어 GitHub `main` 에 올린다. 기존 이력은 레포 안 `archive/pre-public` 브랜치(올리지 않음)와 `git bundle` 파일로 보관한다. `feat/web-script-names` 는 `main` 에 합침(2026-11-05). `feat/app-release` 는 업데이트 작업 후 합친다(사용자 결정) — 새 이력 뒤에 합치면 그 브랜치를 새 `main` 위로 옮겨 붙인다.
5. **원격** — `origin = https://github.com/onedark23/<레포>.git`(GitHub CLI `onedark23` 인증 — 이 PC 의 SSH 키는 다른 GitHub 계정에 묶여 있다). 사내 배포 레포(비공개 Bitbucket) 원격은 SSH 주소(Bitbucket SSH 주소 변경 2026-11-12). 레포 간 연결(`link:../euta-engine/...`)은 그대로 — 다섯 레포를 같은 상위 폴더에 나란히 클론한다(`euta-workspace` README 에 안내).
6. **앱 업데이트** — electron-builder `publish` 를 `github`(owner `onedark23`, repo `euta-app`)로. Windows · Linux 는 electron-updater 가 GitHub Releases 에서 받는다. 서명 없는 맥은 `releases/latest/download/latest-mac.yml` 을 직접 읽어 새 버전을 알린다 — GitHub API(비로그인 IP 당 시간당 60회)는 쓰지 않는다(사무실은 IP 하나로 나간다). 클라우드 업데이트 경로(C9)는 **사내 미러로 유지**(사용자 결정 2026-11-05) — `feat/app-release` 에서 GitHub Releases 방식을 먼저 작업한 뒤 합친다. `MIN_APP_VERSION`(`APP_TOO_OLD`)은 그대로.

## 대안

- **회사 Bitbucket 에 그대로**: 레포를 하나씩 받아야 하고 회사 소유. 사용자가 개인 제품으로 결정.
- **기존 이력 그대로 공개**: 회사 배포 값이 이력에 남는다. 이력 다시 쓰기(filter-repo)는 빠뜨릴 위험이 있어 새 이력이 단순하다.
- **`k8s/dev` 를 GitHub 에 두고 값만 비우기**: 회사 운영 변경(이미지 태그 커밋)이 공개 레포 이력에 계속 쌓인다. 회사 레포로 분리.

## 검증 (할 일)

- 1~2 뒤: 클라우드 단위 · 웹 E2E · 앱 단위 · 앱 E2E 통과, `kubectl kustomize` 로 회사 레포 렌더 확인.
- push 전: 레포마다 올라갈 파일 목록 + 회사 값 검색(회사 도메인 · 테넌트 · 사무실 IP · 사내 저장소 · 네임스페이스 · 대상 서비스 이름) 0건.
