# ADR - 041 앱 업데이트 배포 클라우드 구현

## 상태

채택 (2026-10-30, 단계 17 클라우드 구현). 코드: `euta-cloud` 브랜치 `feat/app-release`.

## 맥락

- [SPEC_앱-배포-업데이트](SPEC_앱-배포-업데이트.md) 은 euta cloud 서버가 앱 설치 · 업데이트 파일을 직접 내려주고(electron-updater generic provider), 관리자만 올리며, 채널별 최근 3개만 남기고, `MIN_APP_VERSION` 미만 앱 요청을 `426 APP_TOO_OLD` 로 막도록 정했다.
- 정하지 않은 구현 세부: 파일 · 상태를 어디에 어떻게 두는지, "게시하면 `latest*.yml` 이 원자적으로 바뀐다" 를 어떻게 지키는지, 1GB 업로드를 서버가 어떻게 받는지, 앱 장치 토큰을 무엇으로 구별하는지, 파일 이름에서 플랫폼을 어떻게 아는지.
- 앱 쪽(업로드 스크립트 · 업데이터)과는 `~/.cache/euta-wt/API_CONTRACT.md` 로 계약을 맞췄고, 아래 결정 중 계약에 닿는 것은 그 파일 "변경" 에도 적었다.

## 결정

### 1. 저장 — DB 두 표 + 버전별 폴더

- 표 `app_releases`(버전 · 채널 · 노트 · `draft`/`published` · 게시 시각) 와 `app_release_files`(릴리스 · 이름 · 크기 · sha512). 마이그레이션 `0005_app_releases.sql` 은 새 표만 만들어 기존 데이터와 무관하다.
- 파일은 `UPDATES_DIR`(기본 `data/updates`, k8s `/data/updates` — 결과 파일과 같은 PVC, 다른 폴더)의 `<채널>/<버전>/<이름>`. 초안이든 게시본이든 같은 자리에 두고 옮기지 않는다.
- 버전은 전 채널에서 하나뿐(유일 색인). 채널은 버전에서 정한다 — prerelease 첫 이름(`0.1.0-alpha.3` → `alpha`), 없으면 `stable`. build metadata(`+…`) · `v` 접두사 · 숫자로 시작하는 prerelease 는 거절(경로에 그대로 쓰이므로).
- 대안: 파일 목록을 `app_releases.files` jsonb 한 칸에 — 업로드 스크립트가 파일을 병렬로 올리면 갱신이 서로 덮는다. 표를 나눠 `(release_id, name)` upsert 로 했다.

### 2. 게시 전환 — "그 이름의 파일을 가진 가장 최근 게시본" 을 요청마다 찾는다

- `GET /updates/<채널>/<이름>` 은 DB 에서 그 채널 게시본 중 그 이름의 파일이 있는 것을 `published_at` 최신 순으로 하나 골라 그 폴더에서 준다. 게시 = 행 하나의 `status`·`published_at` UPDATE 라서, `latest-mac.yml` · `latest.yml` · `latest-linux.yml` 이 한 번에 같이 바뀐다(파일 rename 여러 번이면 사이에 섞인 상태가 보일 수 있다).
- 한 버전에 리눅스 빌드를 빠뜨려도 `latest-linux.yml` 은 직전 게시본 것이 계속 나간다 — yml 이 가리키는 파일 이름에 버전이 들어 있어, 같은 규칙으로 그 파일도 직전 게시본에서 찾아진다.
- 대안: 게시 때 `latest*.yml` 을 채널 폴더로 복사(임시 파일 → rename). 파일 하나씩은 원자적이지만 여러 yml 사이 · yml 과 설치 파일 사이가 어긋날 수 있고, 지난 버전 경로(`/<버전>/<이름>`)를 따로 관리해야 한다.
- "최신" 은 버전 크기가 아니라 게시 순서다(계약: 게시하면 이 버전으로 바뀜). 낮은 버전을 나중에 게시하면 그것이 최신이 된다 — 되돌리기에 쓸 수 있고, electron-updater 는 기본으로 낮은 버전으로 내려가지 않는다.

### 3. 최근 3개 유지 — 게시 트랜잭션 안에서

- 게시 트랜잭션에서 그 채널 게시본을 최신 순으로 세어 4번째부터 행을 지우고(파일 행은 cascade), 커밋 뒤 그 버전 폴더를 지운다. 초안과 다른 채널은 건드리지 않는다. 결과 파일 상한(`RESULT_MAX_TOTAL`) 과 따로다.
- 시간마다 도는 정리 작업에 넣지 않은 이유: 게시가 유일하게 개수를 늘리는 동작이라 그때 정리하면 된다.

### 4. 업로드 — 통과 파서 + 직접 상한 + 임시 파일

- Fastify `bodyLimit` 는 본문을 버퍼로 읽는 파서에만 걸린다. 이 경로(`PUT …/files/:name`, `application/octet-stream`)는 로컬 실행 올리기처럼 본문 스트림을 그대로 넘기는 파서를 쓰고, 상한 1GiB 는 직접 지킨다 — `Content-Length` 가 넘으면 읽기 전에 413, 없거나 거짓이면 세면서 넘는 순간 끊는다. 앱 전체 `bodyLimit`(1MB)은 그대로다.
- 버전 폴더 안 `.upload-<uuid>` 에 쓰면서 SHA-512 를 함께 계산(base64 — electron-builder `latest*.yml` 과 같은 표기) → 끝나면 최종 이름으로 rename → 파일 행 upsert. 같은 이름 재업로드는 덮어쓴다(재시도). 실패 · 끊김이면 임시 파일을 지운다. 받는 사이 초안이 지워지거나 게시되면 파일을 버린다(409).
- 파일 이름은 `[A-Za-z0-9][A-Za-z0-9._-]*` 이고 확장자가 `.dmg` · `.zip` · `.exe` · `.AppImage` · `.blockmap` · `.yml` 중 하나여야 한다(그 밖 400 `UNSUPPORTED_FILE`). 점으로 시작하는 이름을 막아 임시 파일과 겹치지 않는다.
- k8s: 본문 1g 는 이 경로만 받도록 두 번째 Ingress(`euta-server-release-upload`, `/api/admin/app-releases`, `proxy-body-size: 1g` · `proxy-request-buffering: "off"` · 1시간 타임아웃, 같은 호스트 · TLS · 사무실 IP 허용 목록). 나머지 공개 경로는 2m 그대로.

### 5. 내려주기 — `@fastify/send`

- 정적 파일 플러그인(`@fastify/static`)은 웹 화면에 이미 쓰고 있어 같은 앱에 두 번 등록하면 `reply.sendFile` 장식이 겹친다. 그 플러그인이 내부에서 쓰는 `@fastify/send` 를 직접 써서 Range(206) · ETag · Last-Modified 를 받는다. Content-Type 은 확장자 표로 직접 정한다(yml `text/yaml`, dmg · exe · zip 각각).
- `*.yml` 은 `cache-control: no-store`, `/<채널>/<이름>` 의 파일은 다음 게시로 바뀔 수 있어 60초, `/<채널>/<버전>/<이름>` 은 내용이 안 바뀌어 1일 + immutable. 설치 파일은 `content-disposition: attachment`.
- **여러 구간 Range 는 지원하지 않는다**(`@fastify/send` 가 단일 구간만 206, 여러 구간이면 전체 200). Windows 차등 업데이트는 앱의 generic provider 에 `useMultipleRangeRequest: false` 를 두어 구간마다 요청하게 한다(계약 변경 기록).
- 없는 파일 · 초안 파일은 JSON 404. 웹 SPA 대체 응답(모르는 GET → `index.html` 200)이 `/updates/` 에는 걸리지 않게 했다 — electron-updater 가 HTML 을 yml 로 읽는 일을 막는다.
- 공개 경로(`/updates/*` · `/api/app/releases` · `/api/app/compat`)는 인증 훅이 있는 `/api` 범위 밖에 둔다 — 잘못된 토큰을 들고 와도 401 이 아니고, 아래 426 검사도 받지 않는다.

### 6. 관리자 확인 — 웹 세션 또는 읽기·쓰기 개인 토큰

- 기존 관리자 API(가입 승인 등)는 웹 세션만 받는다. 릴리스 올리기는 CLI(`pnpm release:upload`)가 하므로 **관리자 계정의 개인 토큰**도 받되, 토큰은 `read_write` 만(읽기 전용 토큰이 서버 내용을 바꾸지 않게). 웹 화면의 게시 · 삭제는 관리자 세션으로 같은 경로를 쓴다.

### 7. 최소 앱 버전 — 장치 토큰 구별 · semver

- "앱 장치 토큰으로 인증된 요청" = `Authorization: Bearer <euta_ 로 시작하지 않는 값>` 으로 세션이 잡힌 요청. 장치 승인(RFC 8628)으로 받은 토큰은 Better Auth 세션 토큰이고 bearer 플러그인으로 들어오며, 웹은 쿠키, MCP 는 `euta_` 개인 토큰, 러너는 내부 리스너라 섞이지 않는다. 세션 표에 장치 표시를 새로 두는 대신 요청 모양으로 구별했다(마이그레이션 · Better Auth 훅 추가 없음).
- 검사는 `/api` 범위의 인증 훅 바로 뒤 — 같은 범위의 SSE(`/api/me/events` · 프로젝트 변경)도 연결할 때 걸린다. `/api/auth/*`(로그인 · 로그아웃 · 장치 승인)와 `/api/app/*` 는 범위 밖이라 옛 앱도 로그인하고 새 버전을 찾을 수 있다.
- 비교는 `semver`(`0.1.0-alpha.2` < `0.1.0-alpha.10` < `0.1.0`). 헤더가 없거나 SemVer 가 아니면 미만으로 본다. `MIN_APP_VERSION` 이 SemVer 가 아니면 서버가 시작하지 않는다(설정 실수를 조용히 넘기지 않음), 비면 검사 안 함.
- 응답 본문은 계약의 `{ code: 'APP_TOO_OLD', minVersion }` 에 서버 공통 `error: { code, message, details }` 를 함께 둔다.

### 8. 파일 분류 — 이름 규칙

- `/api/app/releases` 의 platform · arch · kind 는 파일 이름으로 정한다: `.dmg` mac 설치 · `.zip` mac 업데이트 · `.exe` win 설치 · `.AppImage` linux 설치 · `.blockmap` 앞 확장자 따라 업데이트 · `.yml` meta(arch `null`, `-mac` mac · `-linux` linux · 나머지 win). arch 는 이름에 `arm64`/`aarch64` 가 있으면 arm64, 아니면 x64.
- 그래서 앱 빌드 `artifactName` 은 공백 없이 arch 를 항상 넣는다(권장 `euta-${version}-${os}-${arch}.${ext}`) — electron-builder 기본값(`euta Setup x.exe`, 맥 x64 arch 생략)은 맞지 않는다. 계약 변경 기록에 적었다.
- 대안: 올릴 때 platform · arch 를 쿼리로 받기 — 스크립트가 더 복잡해지고 yml · blockmap 처럼 애매한 것을 사람이 고르게 된다.

### 9. 웹 "앱 내려받기"

- 머리 메뉴 "앱 내려받기"(`/download`, 로그인 사용자). OS 는 user agent 로, CPU 는 User-Agent Client Hints(크로미움)로만 안다 — 사파리 · 파이어폭스의 맥은 Apple 칩/Intel 을 알 수 없어 맥이면 **두 설치 파일을 함께** 크게 보이고(Apple 칩을 먼저), "이 Mac에 관하여" 로 확인하는 법을 적는다.
- 그 밖: 다른 플랫폼 버튼 · 최신 릴리스 노트 · 보관 중인 3개 버전(각각 내려받기) · 처음 설치 경고 넘기는 법(맥 "그래도 열기" · 윈도 SmartScreen [추가 정보]→[실행] · 리눅스 `chmod +x`, 내 OS 를 먼저) · 관리자만 "릴리스 관리"(초안 포함 목록, 게시 · 삭제). 올리기는 CLI 로만.
- 화면 스타일은 이 화면 전용 `pages/download.css` 로 따로 둬 공용 `styles.css` 를 건드리지 않았다.

## 결과

- 서버 테스트 `test/app-releases.test.ts` 11개(이름 · 버전 · 비교 단위, 올리기 수명주기 · 권한 · 413 · NO_UPDATE_META, 공개 경로 · Range · no-store · JSON 404, yml 전환 · 빠진 플랫폼 이어받기, 3개 유지 · 폴더 삭제, 426 규칙 · 면제 · SSE · 미설정). 웹 E2E `e2e/app-download.spec.ts`(맥 · 윈도 · 리눅스 방문자, 내려받기, 지난 버전, 도움말, 관리자 게시 → 가장 오래된 버전 정리).
- 운영: PVC 14Gi 를 결과 파일(상한 10Gi)과 업데이트(≈ 4.5GB)가 함께 쓴다. 결과 실제 사용이 작아(≈ 50MB) 지금은 괜찮지만 결과가 상한 가까이 차면 모자랄 수 있다 — `k8s/dev/README.md` §11 에 확인 명령.
- 한계: 여러 구간 Range 미지원(앱 설정으로 대응) · 버려진 초안은 관리자가 지운다(자동 정리 없음) · 끊긴 업로드가 남긴 임시 파일은 그 요청이 정리하지만 서버가 업로드 중 죽으면 `.upload-*` 가 남는다(초안 삭제 · 3개 정리 때 폴더째 지워짐).
