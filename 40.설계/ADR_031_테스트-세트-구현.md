# ADR - 031 테스트 세트 구현

## 상태

채택 (2026-10-23, 단계 13 구현). euta-cloud `995d1a1` · euta-app `fb4a20c`·`ee4e93d`(로컬 커밋). 앱 단위 168 · 앱 E2E 5개 스펙(개발 빌드) · 클라우드 단위 255 · 웹 E2E 13 통과. 패키징본 E2E 는 아직(사용자가 패키징 후 확인).

## 맥락

- [SPEC_프로젝트-관리 테스트 세트](SPEC_프로젝트-관리.md#테스트-세트-내부-이름-suite) 가 화면 용어("테스트 세트", 내부 이름 `suite` 유지) · 스크립트 탭 안 화면 · 항목별 "항상 실행"을 정했다. 이 ADR 은 SPEC 이 정하지 않은 **저장 모양 · 취소 처리 · 화면 연결**을 기록한다.
- 기존 모양: 앱 `project.json.suites[] = { id, name, scripts: 경로[], envId?, stopOnFailure }`(ADR-016), 서버 `suites.script_ids`(스크립트 id 배열, 이름 변경을 따라감). 클라우드 스위트에는 "실패 시 중단"이 없고(실패해도 다음), 앱의 `stopOnFailure` 는 이 PC 옵션이다(ADR-025).

## 결정

### 1. 데이터 모양 — 기존 목록 옆에 "항상 실행" 목록을 더함 (추가만)

- 앱: `Suite.alwaysRun?: string[]` — 스크립트 **경로**(같은 세트의 `scripts` 부분집합). 비면 필드를 쓰지 않는다. 읽기는 문자열이면서 `scripts` 안에 있는 것만 남긴다 → 필드 없는 옛 `project.json` 은 그대로 읽힌다(이전 없음). 저장 때도 `scripts` 밖 값은 버린다. 스크립트 이름 변경·삭제(`renameScriptRefs`)가 `alwaysRun` 도 고친다.
- 서버: `suites.always_run jsonb not null default '[]'`(스크립트 **id**) · API 본문/응답 필드 `alwaysRun`. 만들기·고치기에서 `scriptIds` 밖 id 는 422. `PATCH` 에 `scriptIds` 만 오면(옛 앱) 남은 항목의 표시는 유지(`기존 ∩ 새 목록`).
- 실행 시점 고정: 자식 실행 행에 `runs.always_run boolean`(요청 때 스위트에서 복사). 실행 도중 세트를 고쳐도 그 실행의 취소 규칙은 바뀌지 않고, 예약 재실행(`enqueueRetry`)도 그대로 복사한다. 실행 DTO 에 `alwaysRun`.
- 마이그레이션 `0003_suite_always_run`(컬럼 2개 추가, 기본값 있음 — 기존 행 영향 없음).
- 동기화: 클라우드 → 앱 작업 사본은 id → 경로(`scripts[].path`), 앱 편집·올리기는 경로 → id(작업 사본 `scripts[p].id`, `scriptIds` 와 같은 변환). `alwaysRun` 이 없는 옛 서버 응답이면 표시 없음으로 읽는다.
- 같은 스크립트가 세트에 두 번 들어 있으면 표시는 그 스크립트의 **모든 자리**에 적용된다(경로/id 단위). 정리 스크립트를 일부러 두 번 넣는 경우는 드물다고 보고 받아들인다.

대안:
- 항목을 객체로 바꾸기(`scripts: [{ path, alwaysRun }]`) — 한 항목씩 정확하지만 저장 모양이 바뀌어 옛 앱·옛 서버·MCP 응답과 호환 읽기가 필요하다. 추가만으로 끝나는 쪽을 골랐다.
- 순번(index) 목록 — 중복은 정확하지만 순서를 바꾸거나 빼면 표시가 엉뚱한 항목으로 옮겨 간다.

### 2. 실행 규칙

- 앱 실행기(`suite-runner.ts`): 차례가 된 항목이 "실패 시 중단" 이후거나 취소 이후면 건너뜀 — **단 `alwaysRun` 항목은 실행**. 진행 중인 스크립트는 원래대로 끝까지(엔진 중단 API 없음) → "끝난 뒤 남은 항상 실행만" 이 자연히 된다. 상태(최악값)에 포함. `SuiteRun.items[].alwaysRun` 을 남겨 History·카드가 표시한다.
- 클라우드 취소(`cancelRun`): 스위트 부모 취소는 표시 없는 자식만 대상 — 대기 중이면 바로 `cancelled`, 실행 중이면 지금처럼 러너에 중지 요청. 표시된 자식은 **대기면 대기로 남고**(앞 형제가 모두 끝나면 claim 됨 — 기존 claim 조건 그대로), **실행 중이면 끝까지** 간다. 다시 취소해도 표시된 자식은 멈추지 않는다(시간 제한이 상한). 부모는 모든 자식이 끝나면 `cancelled` 로 닫히고 요약 수에 항상 실행 결과가 들어간다.
- 클라우드에는 "실패 시 중단"을 더하지 않았다(SPEC·결정에 없음). 그래서 클라우드에서 "항상 실행"이 바꾸는 것은 취소뿐이다. 앱의 "실패 시 중단"은 이 PC 실행에만 적용된다(카드에 안내).
- 로컬 프로젝트를 클라우드로 올릴 때 이 PC 옵션 "실패 시 중단"도 새 작업 사본으로 옮긴다(전에는 꺼진 채로 만들어짐).

### 3. 화면 연결

- 실행 탭의 실행 위치(`where`)를 `App` 상태로 올려 실행 탭과 스크립트 탭이 같이 쓴다 — 테스트 세트 [▶ 실행]이 "실행 탭의 선택을 따름". 클라우드 실행은 실행 탭과 같은 사전 검사(`useCloudPrecheck` 재사용)를 통과해야 버튼이 켜지고, 시작하면 Live 로 간다(지금 실행 탭과 같음). 항목별 진행·[취소]는 이 PC 실행만 카드에 보인다(클라우드 실행의 항목 진행은 Live 의 행).
- 최근 결과: 이 PC 실행은 `history.list().suiteRuns`(세트 id), 클라우드 실행은 `cloud.history()` 의 스위트 실행(`CloudRunItem.suiteId` 를 새로 채움) 중 더 최근 것. 클라우드 실행의 첫 실패 스크립트는 그 실행의 자식을 한 번 읽어 찾는다.
- 편집 권한: 클라우드 프로젝트의 세트 편집은 서버 설정이라 프로젝트 설정과 같은 조건(온라인 + 보기 역할 아님). 보기 역할은 이 PC 실행도 숨김(기존 규칙). "테스트 세트에 넣기" 체크 칸도 편집 가능할 때만.
- 스크립트 목록 [테스트 세트에 넣기]: 고른 스크립트를 목록 순서로, 기존 세트면 아직 없는 것만 뒤에 붙인다.

### 4. 문구와 오류

- 화면에 보이는 "스위트"는 모두 "테스트 세트"(앱 화면·작업 로그 요약·History·예약, 웹 화면·작업 로그 요약·Teams 카드 대상 라벨, 원격 MCP 의 한국어 오류 1건). 내부 이름·API 경로·필드·작업 로그 종류(`suite.*`)·파일 이름은 그대로.
- 영어 API/검증 오류 문구(`suite not found` 등)는 바꾸지 않았다 — 영어 문구에 "스위트"가 없고, 서버 오류는 MCP·테스트가 같이 쓴다.

### 5. 함께 고친 서버 결함

- `suiteUpdateSchema = suiteCreateSchema.partial()` 은 zod 4 에서 기본값(`scriptIds: []`)을 채워 넣어, 이름·환경만 바꾸는 `PATCH`(앱이 보내는 모양)가 항목을 비웠다. 고치기 스키마는 기본값 없이 따로 둔다.

## 결과

- 옛 파일·옛 서버·옛 앱 어느 조합에서도 읽기가 깨지지 않는다(옛 앱은 표시를 못 볼 뿐, 서버가 남은 항목의 표시를 유지).
- 클라우드 표시된 자식은 취소로 멈출 수 없다 — 정리 스크립트가 멈춰 있으면 시간 제한까지 간다.
