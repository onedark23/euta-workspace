# ADR - 026 앱 클라우드 실행 위임 구현

## 상태

채택 (2026-10-21, C3 앱 쪽 구현). macOS(arm64)에서 앱 단위 테스트와 **실제 로컬 euta cloud 서버 + 실제 러너 프로세스** 대상 앱 E2E(개발 빌드 + 패키징본)로 검증했다. 결과는 아래 "결과" 절.

## 맥락

- [SPEC_클라우드-앱-연동](SPEC_클라우드-앱-연동.md) 의 C3 항목(실행 위치 선택 · 로컬 실행 올리기 · History · 결과 회수 · 예약 탭 · 앱 알림)과 PLAN 결정 "secrets 규칙 적용 범위"(로컬 실행에도 secrets 사용 위치 제한 + 허용 도메인)를 앱에 구현한다. 서버 쪽은 C3 서버 구현 완료 상태([SPEC_클라우드-실행-예약](SPEC_클라우드-실행-예약.md) Change Log 2026-10-21).
- 서버 쪽 사실(euta-cloud 코드로 확인): 실행 요청 `POST /runs`(422 `error.details` = 사전 검사 문제 배열, 하루 상한은 `DAILY_RUN_CAP_REACHED` + `{cap, used, day}` 객체), `POST /runs/precheck` 200 `{ok, problems}`, 피드 `run.requested·leased·started·progress(currentStep·stepsDone)·finished·cancelled·cancel_requested·flaky·skipped·uploaded`(data 에 `runId`, 스위트 자식은 `parentRunId`), `RunDetailDto.steps`, `RunDto` 에 엔진 실행 id 없음, 결과 파일 `GET …/files` + `…/files/*`, 업로드 `POST …/runs/upload`(tar, 맨 위 `run.json`, run.json 의 `scriptHash`·`scriptPath`), `/api/me/events` `ready`/`resync`/`notification`, 404 는 `/api/*` 에서 JSON.

## 결정

### 1. 모듈 — `src/main/cloud/` 에 3개 추가

| 모듈 | 하는 일 |
|---|---|
| `runs.ts` `CloudRuns` | 실행 위치 "클라우드"(로컬 차단 사유 → 서버 사전 검사 → 요청 → Live), 피드 `run.*` 반영, 취소, History 의 클라우드 쪽(목록·스위트 자식), 열기 = 결과 파일 내려받기(캐시·LRU), 클라우드에 올리기(tar) |
| `schedules.ts` `CloudSchedules` | 예약 목록·추가·수정·켜기/끄기·삭제(스크립트 경로 ↔ 서버 스크립트 id), 주기 문구 |
| `notifications.ts` `CloudNotifier` | `/api/me/events` 읽기 → OS 알림 문구, 위치 저장, 앱 꺼진 동안 몰린 알림 접기 |

- 셋 다 Electron 비의존이고 `CloudService` 가 좁은 host 인터페이스(`call`·`online`·`cloudId`·`wc`·`projects`·`live`·`changed`)로 붙인다. `CloudService.call(fn, raw)` 의 `raw` 는 4xx `CloudError` 를 그대로 넘겨 코드·details 를 읽게 한다(하루 상한·사전 검사 문구).
- 클라이언트: 원문 본문 요청(`send` 의 raw 옵션, 업로드·내려받기 시간 제한 10분), SSE 읽기를 `sse()` 하나로 묶어 프로젝트 피드와 앱 알림이 같이 쓴다.
- tar 는 `tar-stream`(서버·러너와 같은 라이브러리) — 직접 ustar 를 짜지 않는다(긴 경로·pax 를 서버와 같은 규칙으로).

### 2. 실행 위치 · Live

- Run 탭에 "실행 위치: 이 PC / ☁ 클라우드"(클라우드 프로젝트, 보기 역할 아님, 기본 이 PC). 스크립트 목록의 "☁ 실행" 은 실행 위치를 클라우드로 둔 Run 탭을 연다. 스위트 영역도 같은 실행 위치를 쓴다.
- 클라우드 선택 시 대상·환경이 바뀔 때마다 사전 검사: **앱이 먼저** 보내기 대기 스크립트("먼저 보내기")·클라우드에 없는 스크립트·오프라인·보기 역할을 걸러 서버 호출 없이 사유를 보이고, 그다음 `POST …/runs/precheck` 문제를 코드별 한국어로 바꿔 버튼 옆에 보인다(사유가 있으면 버튼 비활성). 요청 422 도 같은 문구(하루 상한은 "오늘 클라우드 실행 상한에 도달했습니다 — 사용/상한 (날짜)").
- 요청 본문 = `{scriptPath | suiteId, environmentId, vars, source: 'app'}` — vars 는 Run 탭의 Vars 줄, Env 덮어쓰기·headless·브라우저는 이 PC 실행만.
- **Live 의 클라우드 실행은 엔진 이벤트를 흉내 내지 않는다.** 피드 `run.progress` 에는 현재 단계·완료 수만 있으므로, `run.*` 피드 행마다(실행별 300ms 디바운스) `GET …/runs/:id` 를 다시 읽어 `RunDetailDto` → `RunView` 로 통째 바꾼다(`LiveStore.setCloudRun`, `RunSource` 에 `cloud`). 스위트는 자식 스크립트를 행으로. `RunView.cloud` = 서버 상태·출처·실행 위치·요청자·취소 가능. 프로젝트를 열면 대기·실행 중인 실행을 먼저 채운다.
- 피드 경로: `ProjectSync` 의 `run.*`·`schedule.*` 를 새 `SyncHost.runEvent` 로 넘긴다(작업 사본은 건드리지 않음). History·예약 탭은 `cloud:runs-changed` 로 다시 읽는다.
- 이미 끝난 클라우드 실행이 피드 따라잡기로 Live 에 들어와도 선택을 빼앗지 않는다(재기동 직후 History 열기와 겹침). 클라우드 실행은 작업 사본 지우기를 막지 않는다(서버에서 계속됨).

### 3. History 병합 · 결과 회수

- 렌더러가 로컬 목록(`index.sqlite`)과 클라우드 목록(`GET …/runs?limit=100`, 최상위만)을 `mergeHistory`(공용 순수 함수)로 합친다. 정렬 키 = 시작 → 예약 시각 → 대기 등록 시각(건너뜀은 시작이 없음). 열: 출처(`이 PC · 앱/AI/MCP/스위트` · `클라우드 · 웹/앱/AI/예약/로컬 올림`) · 실행 위치(`이 PC` · 러너 위치). 필터에 "클라우드".
- **이 PC 가 올린 실행은 한 번만** — `RunDto` 에 엔진 실행 id 가 없어 서버만으로는 로컬 실행과 그 "로컬 올림" 쌍을 못 잇는다. 작업 사본의 `cloud-uploads.json`(로컬 run id → 클라우드 run id)으로 로컬 행에 "☁ 올림" 을 달고 클라우드 쪽 쌍은 숨긴다(두 번 올리기도 막음).
- 열기: 결과 파일이 있으면 `cloud-runs/<runId>/` 로 내려받아(임시 폴더 → 끝나면 rename, 경로 탈출 항목 건너뜀) `steps.jsonl` 을 지금의 Live 재생으로 연다. Live id = run.json `id`(엔진 실행 id). **steps.jsonl 의 `run.started.runDir` 는 러너 임시 폴더라 재생 뒤 `runDir` 를 캐시 폴더로 고친다**(스크린샷·리포트). 리포트는 캐시의 `report.html`. 스위트 부모·파일 없음·**파일 만료**(`resultFiles: expired`)는 서버 요약을 Live 에 보이고 History 에 "파일 만료".
- 캐시 상한 2GB 는 **모든 작업 사본 합계**, 실행 폴더마다 `.euta-cache.json`(bytes·lastUsed) — 내려받을 때마다 오래 안 연 것부터 지운다(방금 받은 것은 제외).

### 4. 클라우드에 올리기

- History 의 로컬 행 "☁ 클라우드에 올리기"(클라우드 프로젝트, `run.upload` 권한, 온라인). run.json 의 `scriptPath`(작업 사본 절대 경로)를 `scripts/` 기준 상대 경로로 바꿔 `scriptPath` 로, `meta.envId` 는 클라우드 환경 UUID 로(없으면 `environmentName`).
- tar = 실행 폴더 **내용**(맨 위 `run.json`, 그다음 나머지 파일 정렬). 메모리에 모아 보낸다(PoC 크기 — 서버 상한 `RESULT_MAX_RUN` 2Gi 를 넘는 큰 실행은 한계).
- 응답의 `script.version`·`localModified` 로 "클라우드 버전 vN 에 연결" / "로컬 수정본" 을 보인다.

### 5. 예약 탭

- 클라우드 프로젝트에만 "예약" 탭. 목록(대상·환경·주기 문구·다음 실행·마지막 실행·켜짐·경고 "최근 3회 평균이 간격보다 김")과 편집기(이름·대상(서버에 있고 보내기 대기 아닌 스크립트 또는 스위트)·환경·프리셋/cron·시간 제한·실패 시 1회 재실행·켜짐). 편집자 이상 + 온라인만 편집, 보기 역할은 읽기만. 상단에 "앱·PC 가 꺼져 있어도 서버가 돌린다" 안내.

### 6. 앱 알림

- 온라인이 되면(또는 설정을 켜면) `/api/me/events` 를 읽는다. 위치(`lastEventId`)는 `<userData>/cloud/notify.json`(서버 주소별) — **앱이 꺼져 있던 동안의 알림도 다음 시작 때 받는다.** 스트림을 연 시각보다 1분 넘게 오래된 알림이 4건 이상 몰리면 "앱이 꺼져 있는 동안 클라우드 알림 N건" 1건으로 접는다. `resync` 는 위치만 옮긴다.
- 문구: 예약 결과 = `[euta] 실패|회복|통과|통과 · 불안정|건너뜀|중단 — <대상>`, 내 실행 종료 = `클라우드 실행 끝: <상태> — <대상>`, 본문 = 프로젝트 · 환경 · 예약 이름 · 실패 단계 · 소요. 클릭 → 창 앞으로 → 그 프로젝트 열기 → 그 실행 열기(내려받아 Live).
- 앱 설정 > 클라우드 "앱 알림"(`AppSettings.cloudNotify`, 기본 켬). 끄면 연결을 끊고 위치를 지운다(다시 켜면 "지금부터" — 쌓인 알림 폭주 없음).
- E2E 는 OS 알림을 볼 수 없어 `EUTA_E2E` 에서 표시하지 않고 기록만(`__eutaTest.notifications()`·`clickNotification(i)`).

### 7. secrets 규칙 — 모든 로컬 실행 (PLAN 결정 2026-10-21)

- 엔진에 `restrictSecrets`(사용 위치 제한만, [ADR-024](ADR_024_엔진-클라우드-보완.md) 결과)를 더하고, 앱은 실행 조립(`assembleRun`)이 항상 `restrictSecrets: true` + 환경의 허용 도메인을 낸다 → 실행 버튼·스위트·스크립트 상세 실행(`startRun`), 앱 AI 채팅(`aiServerConfig` → 엔진 도구 핸들러 `ServerConfig.restrictSecrets`·`allowedDomains` → `run_script`·`session_*`·`validate_script`), 고급 터미널(`EUTA_RESTRICT_SECRETS=1`·`EUTA_ALLOWED_DOMAINS=<프로젝트 환경 허용 도메인 합집합>` → 플러그인이 띄우는 엔진 MCP 서버가 읽음). 터미널 추가 환경변수는 7개가 되었다(인증 관련 없음, ADR-011 정책 유지).
- 허용 도메인: 로컬 환경 `allowedDomains`(없으면 환경 주소 호스트 — **기본값은 파일에 쓰지 않고 쓸 때 계산**, 옛 project.json 그대로 호환), 설정 화면에서 쉼표 목록 편집·"주소 호스트로 되돌리기"(null). 입력은 호스트로 정규화(스킴·경로·포트 제거, `*.`·앞뒤 점), 잘못된 값 거절, 20개까지. 클라우드 프로젝트의 이 PC 실행 = 서버 환경의 목록.
- 위반 문구는 한국어로 바꿔 보인다(`koSecretRule` — Live 의 실행 오류·단계 오류·"validation failed" 로그, Run 탭 검증, 스크립트 상세 경고). 스크립트 상세에서는 **저장을 막지 않는 경고**(`ruleIssues`) — 서버 저장 규칙도 위치 위반을 막지 않고 사전 검사에서만 거절하므로 같게.
- Live 는 이전에 "validation failed" 로그를 보이지 않았다 → `log`(phase input, level error)를 실행 오류로 보이고, `run.finished` 가 오류 없이 와도 지우지 않게 했다.

## 고려한 대안

| 대안 | 제외 이유 |
|---|---|
| 피드 `run.*` 를 엔진 이벤트로 바꿔 `applyEvent` 로 흘리기 | 피드에 단계 이벤트가 없어(현재 단계·완료 수만) 타임라인을 못 만든다. 서버 상세를 다시 읽는 쪽이 단순·정확 |
| 클라우드 실행도 결과 파일을 즉시 전부 받기 | PLAN "요약은 즉시, 파일은 열 때" · 영상 용량 |
| 로컬 run ↔ 올림 쌍을 서버 응답으로 잇기 | `RunDto` 에 엔진 run id 가 없다(서버 변경은 이 작업 범위 밖) → 작업 사본 기록으로 |
| 알림 위치를 메모리에만 | 앱이 꺼진 동안의 예약 실패를 놓친다(완료 기준 "재기동 시 반영"의 취지와 어긋남). 몰림은 접기로 해결 |
| 앱 밖 단독 MCP 서버·CLI 의 기본값도 켜기 | SPEC_프로젝트-관리 "앱 밖에서 단독으로 쓰는 MCP 서버·플러그인 동작은 바꾸지 않는다" — 환경변수·플래그로 켜게 두고 앱(터미널)이 켠다 |
| 스크립트 상세에서 위치 위반 저장 거부 | 서버는 저장을 받는다(사전 검사만 거절). 같은 스크립트가 클라우드·로컬에서 저장 규칙이 달라지지 않게 경고로 |

## 한계·후속

- 업로드 tar 를 메모리에 모은다(대용량 영상 실행은 메모리 사용이 큼). 필요하면 스트리밍 업로드로.
